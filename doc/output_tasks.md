# AI 新闻 Agent 多格式输出任务分解

> **依据：** [doc/output_format.md](output_format.md)
>
> **目标：** 在保持现有 Markdown 报告行为兼容的前提下，新增 HTML 和 PDF 输出，并支持单次命令生成一种或多种格式。
>
> **实施原则：** 先统一报告数据与渲染接口，再实现 HTML、PDF，最后完成 CLI 编排和文档。优先使用离线、确定性的单元测试，不将真实新闻抓取或真实 LLM 调用作为常规验收前提。
>
> **状态约定：** `[ ]` 未开始，`[~]` 进行中或尚有验收项待验证，`[x]` 已完成。以下状态根据当前代码、自动化测试和本地检查结果更新。真实 PDF 渲染、中文字体与分页仍需在安装并配置 WeasyPrint 的环境中验证。

## 1. 任务总览

| 阶段 | 任务范围 | 主要产出 | 前置阶段 |
| --- | --- | --- | --- |
| O1 | 报告数据模型与 Markdown 重构 | 统一数据查询、Markdown Renderer、兼容性测试 | 无 |
| O2 | HTML 输出 | HTML Renderer、模板/CSS、HTML 文件写入 | O1 |
| O3 | PDF 输出 | PDF Renderer、可选依赖、中文与分页处理 | O2 |
| O4 | 多格式 CLI 与统一编排 | `--formats`、多格式输出、错误汇总 | O1；集成 O2、O3 |
| O5 | 回归验证与文档完善 | 测试覆盖、README 和使用说明更新 | O2、O3、O4 |

建议按 O1 → O2 → O3 → O4 → O5 顺序实施。O4 的部分 CLI 参数解析工作可提前开发，但在三个渲染器和统一编排稳定后再完成整体验收。

## 2. 现有实现与兼容性约束

当前实现主要位于：

- `src/newsagent/agents/report.py`：提供 `ReportData`、`build_report_data()`、兼容入口 `build_report()` / `write_report()`，以及多格式编排入口 `write_reports()`。
- `src/newsagent/agents/report_renderers/`：包含 Markdown、HTML 与可选 PDF Renderer。
- `src/newsagent/cli/main.py`：`news report` 支持 `--hours` 和 `--formats`，默认只生成 Markdown。
- `tests/test_p7.py`、`tests/test_report_formats.py`、`tests/test_report_cli.py`：覆盖原有报告兼容性、多格式编排、HTML 转义、来源链接安全、CLI 错误处理与缺少 PDF 依赖的行为。
- `pyproject.toml`：PDF 引擎声明在可选依赖组 `pdf` 中，不是普通安装的强制依赖。
- `output/`：默认报告输出目录。

实施必须保持以下约束：

1. `build_report()` 继续返回 Markdown 字符串，除非未来另行评估兼容性变更。
2. `write_report()` 不传新参数时仍然只生成 Markdown，并返回一个 `Path`。
3. `news report --hours 24` 继续只生成 Markdown，不得因为安装了可选依赖就自动多生成格式。
4. 原有事件时间窗口、评分排序、头条数量、空报告提示及标题日期规则尽量保持不变。
5. 格式转换只读取本地报告数据，不隐式抓取新闻、不发起 LLM 请求。
6. 不将 PDF 引擎及其系统依赖变为普通项目安装的强制依赖。

# O1：报告数据模型与 Markdown 重构

## TASK-OUT-001：梳理并固定现有报告行为

- [x] **目标：** 明确目前报告查询、排序、标题、时间窗口和输出路径规则，为重构建立可回归的行为基准。
- **检查文件：** `src/newsagent/agents/report.py`、`src/newsagent/cli/main.py`、`tests/test_p7.py`。
- **产出：** 报告行为清单与测试补充。
- **依赖：** 无。
- **验收标准：**
  - 覆盖空报告、有事件报告以及多事件排序。
  - 验证日报/周报的命名规则：`hours <= 24` 使用 `daily`，否则使用 `weekly`。
  - 验证头条与其他事件分组、摘要、影响说明和评分的既有规则。
  - 使用 SQLite 测试 fixture 或 mock，不访问新闻站点、不调用真实 LLM。

## TASK-OUT-002：抽取统一 ReportData 数据模型

- [x] **目标：** 将数据库查询与 Markdown 字符串拼接分开，为不同渲染器提供同一份结构化报告数据。
- **建议文件：** `src/newsagent/agents/report.py`；若结构明显扩大，可新增 `src/newsagent/agents/report_data.py`。
- **建议字段：**
  - `title`：报告标题。
  - `generated_at`：报告生成时间，明确采用的时区。
  - `period_hours`：报告覆盖小时数。
  - `events_count`：选中的事件数。
  - `top_events`：头条事件列表。
  - `other_events`：其他事件列表。
  - 每个事件包含已有字段 `event_id`、`title`、`summary`、`why_it_matters`、`base_score`，并可在确有数据时包含来源 URL。
- **依赖：** TASK-OUT-001。
- **验收标准：**
  - 数据查询只执行一次，并产生有确定排序的结构化数据。
  - 空报告也能生成有效的 ReportData。
  - 所有渲染器使用同一份事件数据、报告日期和时间范围。
  - 不将 HTML 转义、CSS 或 PDF 逻辑放入数据模型。
  - 现有 `build_report()` 调用方式保持兼容。

## TASK-OUT-003：实现 Markdown Renderer

- [x] **目标：** 将现有 Markdown 内容拼接逻辑封装为独立渲染函数。
- **建议文件：** `src/newsagent/agents/report_renderers/markdown.py`；也可按代码规模先在现有模块实现清晰的独立函数。
- **依赖：** TASK-OUT-002。
- **验收标准：**
  - Renderer 输入统一报告数据，输出 Markdown 字符串。
  - `build_report(hours, top_n)` 的返回类型与公开行为保持兼容。
  - 不在 Renderer 中自行查询数据库或调用 LLM。
  - 保留中文标题、头条、其他事件、摘要、影响说明、评分和空报告提示。
  - 现有报告测试通过，且新增测试无需联网。

## TASK-OUT-004：建立报告文件写入与兼容入口

- [x] **目标：** 统一输出目录创建、命名和文本文件写入行为，同时保留旧 API。
- **涉及文件：** `src/newsagent/agents/report.py` 及相关测试。
- **依赖：** TASK-OUT-003。
- **设计建议：**
  - 继续保留 `write_report(hours=24, out_dir=None) -> Path`。
  - 新增后续多格式编排入口，例如 `write_reports(hours, formats, out_dir=None)`，在 O4 接入 CLI。
  - 复用同一个报告生成日期和命名前缀。
- **验收标准：**
  - 不传新参数时只写入 `.md` 文件，并返回 `Path`。
  - 使用 UTF-8 写入 Markdown。
  - 目标目录不存在时自动创建。
  - 同日期、同类型再次生成时的覆盖行为明确且有测试。

### O1 阶段验收

- `build_report()` 与 `write_report()` 的原有调用方式仍可使用。
- 报告测试使用本地数据或 mock，不依赖真实新闻抓取或 LLM 调用。
- HTML 使用 Python 标准库；PDF 使用独立的可选依赖，不污染基础依赖。

# O2：HTML 输出

## TASK-OUT-005：确定 HTML 模板与样式实现方式

- [x] **目标：** 选择简单、可维护的 HTML 生成方式，并确定模板职责。
- **涉及文件：** 建议新增 `src/newsagent/agents/report_renderers/html.py`；如采用模板，可增加 `src/newsagent/templates/report.html` 和独立 CSS 文件。
- **依赖：** TASK-OUT-002。
- **设计选择：**
  - 若内置 HTML 生成逻辑足够简单，可不增加模板引擎。
  - 若采用 Jinja2，应启用自动转义，模板内容与数据保持分离。
  - CSS 应作为本地资源或模板的一部分，不依赖 CDN、在线字体或远程图片。
- **验收标准：**
  - 选型理由和依赖影响清楚。
  - HTML 不需要联网即可打开阅读。
  - HTML 文本编码明确为 UTF-8。

## TASK-OUT-006：实现 HTML Renderer

- [x] **目标：** 将 ReportData 渲染为完整的 HTML5 文档。
- **内容：**
  - 标题、报告日期、时间范围、事件总数。
  - 头条区域与其他事件区域。
  - 事件标题、摘要、影响说明和评分。
  - 仅当输入数据存在有效来源 URL 时显示来源链接。
  - 适合桌面与移动设备的可读布局。
- **依赖：** TASK-OUT-005。
- **验收标准：**
  - 输出包含 `<!doctype html>`、正确的 UTF-8 声明与可读的页面主体。
  - HTML 中的事件顺序、数量和标题与同批 ReportData 一致。
  - 空事件报告能够显示明确的空状态提示。
  - 标题、摘要、影响说明及链接均经过正确转义，恶意内容不能变成可执行脚本。
  - 不进行网络访问或 LLM 调用。

## TASK-OUT-007：实现 HTML 样式与打印布局

- [x] **目标：** 提供适合长篇新闻简报的网页样式，并为 PDF 渲染准备可复用的打印规则。
- **依赖：** TASK-OUT-006。
- **验收标准：**
  - 中文字体设置合理，保留系统字体回退。
  - 标题层级、正文行距、链接、事件分组有明确样式。
  - `@media print` 提供打印布局，避免大面积背景、异常宽度和不必要的装饰。
  - 长标题、长 URL 和特殊字符不会破坏整个版面。

## TASK-OUT-008：实现 HTML 写入及基础测试

- [x] **目标：** 让渲染出的 HTML 按既定文件命名规则保存。
- **输出示例：** `output/daily_YYYY-MM-DD.html`、`output/weekly_YYYY-MM-DD.html`。
- **依赖：** TASK-OUT-006、TASK-OUT-007。
- **验收标准：**
  - HTML 文件编码为 UTF-8，且文件非空。
  - 写入失败时返回明确错误，不将文件误报为成功生成。
  - 测试覆盖普通文本、特殊字符、中文、空报告和带来源链接的事件。
  - 测试只处理本地数据，不抓取真实新闻。

### O2 阶段验收

- 可以通过程序接口独立生成完整 HTML 文件。
- HTML 在离线条件下可阅读，打印布局可用。
- HTML 安全转义和空报告行为有自动化测试。
- 原有 Markdown 路径不受影响。

# O3：PDF 输出

## TASK-OUT-009：确定并隔离 PDF 渲染依赖

- [x] **目标：** 选定 PDF 引擎，避免 PDF 系统依赖影响普通项目安装。
- **推荐方向：** 评估 WeasyPrint，将 HTML 与 CSS 转换成 PDF。
- **涉及文件：** `pyproject.toml`、PDF Renderer 模块、可选安装说明。
- **依赖：** TASK-OUT-006、TASK-OUT-007。
- **验收标准：**
  - PDF 依赖位于可选依赖组，而不是基础依赖。
  - 明确记录目标操作系统所需的系统库与安装注意事项。
  - 对缺少 PDF 库的情况可以检测并给出可执行的安装提示。
  - PDF 方案不依赖远程转换服务。
  - 不假设所有平台安装 Python 包后就无需任何系统依赖。

## TASK-OUT-010：验证中文字体与 PDF 版式

- [~] **目标：** 建立 HTML 到 PDF 的版式规则，提前处理中文、分页与长内容风险。
- **依赖：** TASK-OUT-009。
- **实现要点：**
  - A4 页面、明确页边距和页面背景。
  - 标题与正文的中文字体回退，确认目标环境具备可用字体。
  - 通过 `@page` 和适当的分页规则控制页面布局。
  - 处理长标题、长 URL、代码、emoji、特殊字符及较长事件正文。
  - 在引擎支持时保留可点击链接与页码。
- **验收标准：**
  - 中文标题、正文和常用标点可正确渲染。
  - 长内容能够合理跨页，不会因强制避免分页导致大片空白或页面溢出。
  - 缺少字体或系统依赖时能报告清晰错误。
  - 使用本地样例生成 PDF，不需要访问外部新闻站点。

## TASK-OUT-011：实现 PDF Renderer 与文件写入

- [x] **目标：** 从与 HTML 一致的报告输入生成 PDF 文件。
- **建议文件：** `src/newsagent/agents/report_renderers/pdf.py`。
- **依赖：** TASK-OUT-009、TASK-OUT-010。
- **验收标准：**
  - 输出路径符合 `output/daily_YYYY-MM-DD.pdf` 或 `output/weekly_YYYY-MM-DD.pdf` 的规则。
  - 生成的 PDF 非空，具有有效 PDF 文件签名。
  - 不把 HTML 字符串当成 PDF 文件写入。
  - 缺少依赖、字体或写入权限时，失败结果可被上层识别。
  - 不在 PDF 生成时访问网络、抓取新闻或调用 LLM。

## TASK-OUT-012：增加 PDF 单元和集成测试

- [~] **目标：** 验证 PDF 生成成功、结构基本有效和关键版式情况。
- **依赖：** TASK-OUT-011。
- **验收标准：**
  - 覆盖有事件与无事件两种输入。
  - 检查输出文件非空、PDF 签名及基础文件结构。
  - 在安装 PDF 可选依赖的测试环境中验证中文和较长事件。
  - 缺少 PDF 依赖时验证报错信息清楚。
  - 基础测试环境没有 PDF 依赖时，可明确跳过专用集成测试；不能因为跳过而声称 PDF 集成测试通过。

### O3 阶段验收

- 在文档声明支持的环境中可以通过本地 ReportData 生成 PDF。
- 中文、分页、空报告和长内容得到验证。
- PDF 依赖缺失不会静默生成无效文件，也不会破坏 Markdown/HTML 的独立功能。

# O4：多格式编排与 CLI

## TASK-OUT-013：实现 `--formats` 参数和格式校验

- [x] **目标：** 为 `news report` 增加格式选择参数。
- **涉及文件：** `src/newsagent/cli/main.py` 及 CLI 测试。
- **建议接口：** `--formats md,html,pdf`；未指定时默认 `md`。
- **依赖：** TASK-OUT-004；HTML/PDF 在完整验收时分别依赖 O2/O3。
- **验收标准：**
  - `news report --hours 24` 仍只生成 Markdown。
  - `--formats html`、`--formats pdf` 可分别请求单一格式。
  - `--formats md,html,pdf` 可请求三种格式。
  - 格式名称大小写不敏感，解析后统一为小写并去重。
  - 未知格式在写文件前被拒绝，并列出支持值。
  - `--hours` 默认值与当前行为不变。

## TASK-OUT-014：实现统一 `write_reports()` 编排入口

- [x] **目标：** 在一次报告任务中生成同一份数据的指定格式文件。
- **建议接口：** `write_reports(hours, formats, out_dir=None)`，返回格式到路径的映射。
- **依赖：** TASK-OUT-004、TASK-OUT-008、TASK-OUT-011。
- **验收标准：**
  - 同一次调用只查询一次报告数据。
  - 所有格式共享生成日期、标题、时间范围、事件数及顺序。
  - 同一批数据可分别传递给 Markdown、HTML 和 PDF Renderer。
  - 输出路径以确定的格式名称映射，调用方无需猜测文件名。
  - 旧 `write_report()` 入口仍然可用且不改变默认行为。

## TASK-OUT-015：实现多格式错误汇总与退出码

- [x] **目标：** 防止某一种格式失败时，其余可用格式全部丢失。
- **依赖：** TASK-OUT-014。
- **验收标准：**
  - 每种格式的生成成功或失败都被单独记录。
  - 请求多种格式时，一种格式失败后仍尝试生成其余格式。
  - 如果请求的格式没有可用依赖，明确报告失败原因。
  - 存在任一请求格式失败时，命令返回非零退出码，并列出成功路径与失败格式。
  - 只生成单一 Markdown 时，CLI 输出继续保持简单且兼容的路径形式。
  - 不静默忽略参数错误或渲染错误。

## TASK-OUT-016：统一命名与覆盖行为

- [x] **目标：** 确保三种格式都遵循既有日报、周报命名规则。
- **依赖：** TASK-OUT-014。
- **验收标准：**
  - `hours <= 24` 使用 `daily` 前缀；`hours > 24` 使用 `weekly` 前缀。
  - 扩展名分别为 `.md`、`.html`、`.pdf`。
  - 同次多格式输出共享日期，不在渲染不同格式时各自重新计算日期。
  - 输出目录自动创建。
  - 同名文件覆盖行为有测试和文档说明。
  - 可考虑临时文件成功生成后再替换目标文件，避免留下半成品。

### O4 阶段验收

- 单格式和多格式命令都可用。
- 默认 CLI 行为不变。
- 一次查询即可生成同一批数据对应的多个文件。
- 部分失败行为明确，有成功路径、有错误明细、有正确退出码。
