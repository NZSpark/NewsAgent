# AI News Agent 混合架构设计方案 (Gemini + Local LLM)

综合前期的云端大模型方案与本地部署 (`doc/local_llm.md`) 方案，为了兼顾**处理效果**、**上下文窗口限制**以及**长期运行成本**，我们设计了这套结合云端大模型 (Gemini 1.5) 与本地大模型 (Local LLM) 的混合架构 (Hybrid Architecture)。

## 1. 核心架构与模块划分

系统由以下模块构成，按照“本地初筛 -> 云端精炼”的漏斗模型进行数据流转：

### 1.1 数据源解析与采集 (Source & Fetcher)
- **目标**：从 `doc/sites.md` 获取最新资讯。
- **策略**：
  - 优先通过 `feedparser` 解析 RSS 源。
  - 使用 `trafilatura` 或 `newspaper3k` 提取网页纯文本，去除非核心 HTML（广告、导航栏），以减少后续 Token 消耗。
  - 对动态网页，使用 `Playwright` 渲染后抓取。如果被目标网站封 IP，推荐在爬取阶段引入 `Jina Reader API` (https://r.jina.ai/) 作为中间层，直接获取干净的 Markdown。

### 1.2 状态管理与去重 (State Manager)
- **工具**：本地 `SQLite` 或 `TinyDB`。
- **逻辑**：基于 URL 和时间戳进行哈希对比，确保只处理 24 小时内的新增新闻，避免重复计算。

### 1.3 本地 LLM 预处理引擎 (Local LLM Pre-processor)
- **任务**：成本极低的初筛、垃圾信息过滤、基础分类。
- **技术栈**：`Ollama` 部署 `Qwen-2.5 (7B/14B)` 或 `Llama-3.1 (8B)`。
- **应用场景**：
  - **相关性过滤**：快速判断爬取的正文是否真正属于“AI 新闻”（过滤掉网站的通用公告、招聘启事等噪音）。
  - **实体提取与标签化**：快速抽取出文章中的核心实体，生成 Metadata。
  - *优势*：将海量的原始网页数据在本地进行免费的高效降噪，并解决算力瓶颈耗时问题，通过后台队列异步消化。

### 1.4 Gemini 深度处理引擎 (Gemini LLM Engine)
- **任务**：高难度摘要、多语言翻译、超长文本聚合。
- **优势利用 (Gemini 1.5 Flash/Pro)**：
  - **超大上下文 (1M+ Tokens)**：本地小模型无法一次性吞下数十篇长文，而 Gemini 1.5 可以。将本地初筛后的同主题新闻汇总一次性喂给 Gemini，要求其进行“消除冲突、整合归纳”。
  - **逻辑与翻译**：输出极其流畅的中文化科技简报，排版精美。

### 1.5 产出与分发模块 (Publisher)
- **任务**：生成最终的 Daily Briefing Markdown 文件。
- **分发**：每日早晨自动生成排版好的文档，并通过 Webhook 推送至 Telegram、飞书、钉钉。

## 2. 混合架构工作流 (Workflow)

1. **定时抓取**：Cron Job 触发，并发抓取 `doc/sites.md` 列表内所有站点的更新。
2. **本地去重**：查重数据库，获取全新文章集合。
3. **本地 LLM 漏斗筛选 (异步队列)**：
   - 将新文章排队喂给本地 Ollama。
   - 丢弃低价值/非 AI 相关的文章。
   - 提取出高价值文章的关键信息，做预打标。
4. **Gemini 聚合摘要 (Batch Request)**：
   - 将本地筛选通过的优质文章（携带本地提取的标签）组合成一个超大 Prompt，调用 Gemini API。
   - Gemini 负责将其融合、总结、翻译，生成连贯的“今日 AI 焦点”报告。
5. **推送与存档**：生成 `YYYY-MM-DD.md` 并完成消息通道的推送。

## 3. 为什么选择混合架构？

- **降本增效**：如果全部交由 Gemini 处理，大量杂音和无效文章会消耗大量 API Token。本地 LLM 充当了“免费的门卫”。
- **规避本地算力瓶颈**：本地 7B 模型应对复杂的多文章聚合和长文本推理会产生严重的“幻觉”和遗忘，交给拥有 1M 上下文的 Gemini 1.5 能够最大化质量。
- **灵活切换**：在 Gemini 额度耗尽或网络不可用时，系统可优雅降级完全回退到本地 LLM 输出简单摘要。
