# News Chat 功能任务分解

> 依据：`doc/requirements.md`、`doc/command_support.md`。
>
> 目标：将 News Chat 拆解成可独立实现、验证和验收的任务。本文是任务计划，不代表功能已实现。

## 1. 范围与实施原则

### 1.1 交付目标

实现 `news chat`，满足以下行为：

1. 本地终端与微信 Bot 都能输入消息，并进入同一消息处理流程。
2. 普通文本调用项目既有 LLM 能力生成回复。
3. 以 `/` 开头的输入按允许列表执行已有 NewsAgent 命令。
4. 普通回复、命令结果和错误结果统一广播给本地终端及微信 Bot。
5. `/quit`、Ctrl-C 和终端输入结束均能触发可控的资源清理。
6. 微信消息接收具备游标持久化、消息去重和基本故障恢复能力。
7. 自动化测试默认不访问真实网络，不依赖真实微信账号或在线 LLM。

### 1.2 实施原则

- 优先复用 `src/newsagent/cli/main.py` 中的 `build_parser()` 和已有 `cmd_*` 处理函数，不复制新闻业务逻辑。
- 普通聊天复用 `newsagent.llm` 的统一生成接口；`/ask` 复用 `newsagent.agents.query.answer()`。
- 微信协议操作复用 `ILinkClient`，不另外实现一套 iLink 客户端。
- 命令只能从明确的允许列表中选择；禁止使用 `shell=True` 或执行模型生成的 shell 命令。
- 接收、命令执行与输出投递分层；一个任务的结果只生成一次，两个输出端分别投递。
- 先完成本地终端闭环，再接入微信，降低同时排查多个组件的难度。
- 协议字段、上下文令牌和同步游标的实际行为必须以代码与测试结果为准；未知行为不得伪装成已验证。

## 3. 详细任务

### CHAT-001：明确 Chat 接口、状态及消息模型

**目的：** 先定义输入端、输出端与会话控制器之间的契约，避免终端和微信各自维护不同业务逻辑。

**实施内容：**

- 新增 `src/newsagent/chat/` 包及模块入口。
- 定义统一消息模型，至少包含 `source`、`text`；微信消息可以包含 `message_id`、`sender_id`、`context_token` 等字段。
- 定义统一输出模型，至少包含 `text`、来源类型和是否错误。
- 明确会话状态：`STARTING`、`RUNNING`、`STOPPING`、`STOPPED`。
- 设计输入队列接口、输出接口以及可注入的 LLM、命令分发器和微信客户端，便于离线测试。
- 敏感令牌不可写入普通日志或通用错误对象。

**验收标准：**

- 输入来源通过一个稳定的消息接口表示。
- 核心会话逻辑不直接依赖真实终端或真实微信网络连接。
- 可通过 mock 替换 LLM、命令执行和输出端。

### CHAT-002：建立输出广播器

**目的：** 让所有业务结果走相同的双端输出路径。

**实施内容：**

- 定义终端和微信输出适配器的发送契约。
- 实现广播器，接收一次格式化结果，分别尝试发送给两个输出端。
- 两个通道分别记录成功或失败；一个通道失败不得阻止另一个通道投递。
- 空结果返回清晰提示，不能静默丢弃。
- 为微信长消息定义分段策略，单条长度符合 `ILinkClient` 当前协议限制。
- 广播器不得把发出的消息再次注入输入队列，避免自我回环。
- 广播失败不能触发新闻命令重新执行。

**验收标准：**

- 一个结果分别发送一次到两个已连接的输出端。
- 微信发送抛错时，终端仍收到完整结果。
- 输出通道失败状态可测试并可被会话记录。
- 长文本按规则拆分，分段失败时仍能报告错误且不重复执行源任务。

### CHAT-003：实现普通文本的 LLM 对话

**目的：** 将非命令消息送入项目现有 LLM 生成能力。

**实施内容：**

- 使用项目统一的 `newsagent.llm` 生成接口及已有模型、提供商配置，不另设一套配置系统。
- 定义 NewsAgent 对话系统提示和历史上下文格式。
- 首版将最近有限轮次的对话保存在内存中，例如最近 10 轮；终端和微信共享此上下文。
- 从模型结果中提取面向用户的回复文本。
- LLM 失败时返回可读错误或已有路由的降级结果，并继续保持会话可用。
- 对输入、输出和上下文长度设合理限制。
- 对话历史作为数据输入，不得覆盖系统约束；禁止因模型输出而执行任意 shell 或未授权命令。

**验收标准：**

- 普通终端消息和普通微信消息走相同的对话处理函数。
- 测试可验证 LLM 收到正确消息历史，并只生成一次回复。
- 回复交给 CHAT-002 广播，而非由 LLM 模块直接发微信。
- LLM 异常不会导致整个会话退出。

### CHAT-004：实现斜杠命令解析与安全允许列表

**目的：** 可靠地区分命令和自然语言，并阻止未经授权的命令执行。

**实施内容：**

- 只有首个非空字符为 `/` 时才进入命令解析。
- 使用 `shlex.split()` 解析命令名和参数，支持带引号的空格参数。
- 命令名称按不区分大小写的规则规范化。
- 未知命令返回 `/help` 提示，不送给 LLM 猜测执行。
- `/help`、`/quit` 由 Chat 内置处理。
- 首版允许列表对照 `doc/command_support.md`，覆盖已批准的新闻命令。
- 明确禁止递归 `chat`、`wechat login`、`wechat bind`、`wechat logout`、任意系统命令和不在允许列表的子命令。
- 明确禁止通过命令参数绕过限制，例如 `/report --send-wechat`，避免与统一广播重复发消息。
- 参数解析错误转成用户可读结果，不泄露完整 traceback。

**首版允许命令：**

- `/fetch [--source ID] [--limit N]`
- `/sources`
- `/recent [--hours N] [--limit N]`
- `/search QUERY [--limit N]`
- `/event EVENT_ID`
- `/health`
- `/pipeline [--limit N] [--hours N]`
- `/ask QUESTION`
- `/semantic-cluster [--hours N]`
- `/research [EVENT_ID] [--limit N] [--min-importance F] [--live]`
- `/report [--hours N] [--formats md,html,pdf]`
- `/index [--limit N]`
- `/semantic-search QUERY [--limit N] [--articles]`

**验收标准：**

- 含空格的查询经引号包装后被正确解析。
- 缺参数、未知参数、未知命令均返回清楚的使用提示。
- 任意 shell 文本和未授权子命令一律不能执行。
- 允许列表与 CLI 已注册的命令及参数保持一致。

### CHAT-005：复用现有 CLI 命令并捕获结果

**目的：** 在 Chat 中使用现有业务能力，不重复实现新闻命令。

**实施内容：**

- 通过 `src/newsagent/cli/main.py` 的 `build_parser()` 复用命令解析与参数校验。
- 在安全校验之后调用解析结果的 `args.func(args)`。
- 捕获已有命令写入 stdout/stderr 的内容及返回码。
- 对 `SystemExit`、参数错误和普通异常进行转换，确保一个错误不会终止会话。
- 对输出为空的命令生成简明成功提示。
- 命令分发器串行执行，避免使用 `redirect_stdout()` 时发生全局流竞争。
- 把文件路径、JSON 输出和普通文本统一转换为可广播的文本结果。
- 防止 `/report` 触发 `--send-wechat` 后又被广播器发送一次。

**验收标准：**

- 至少为 `/recent`、`/search`、`/ask`、`/fetch`、`/pipeline`、`/report` 编写分发测试。
- 使用 mock 替换命令函数时可确认参数和调用次数。
- 命令异常返回错误结果并继续处理下一条消息。
- 不通过 `subprocess` 或 `shell=True` 执行命令。

### CHAT-006：实现终端输入适配器

**目的：** 提供本地交互入口，并与微信输入统一。

**实施内容：**

- 逐行读取标准输入，每行生成一个 `source="console"` 的消息。
- 空行忽略；普通文本与命令进入同一个处理队列。
- 终端输出完整结果，支持中文和多行文本。
- 输入读取不能阻塞微信长轮询；建议采用独立线程或可停止的输入适配器。
- 处理 EOF 和输入异常，并通知会话控制器进入清理流程。

**验收标准：**

- 输入普通问题可生成并显示回复。
- 输入允许命令可执行并显示结果。
- 输入读取线程退出后不会留下无法结束的进程。

### CHAT-007：实现会话编排与退出生命周期

**目的：** 建立可启动、可运行、可优雅关闭的 `news chat`。

**实施内容：**

- 新增 `cmd_chat` 并在 `build_parser()` 中注册顶层 `chat` 命令。
- 在会话启动阶段初始化队列、LLM 处理器、命令分发器和终端输入端。
- 串行处理消息，以确定普通回复和命令结果的顺序。
- 实现 `/help`，列出实际启用的命令及参数简述。
- 实现 `/quit`，阻止新任务进入、等待当前任务完成并关闭资源。
- 将 Ctrl-C 转换为同一关闭流程；EOF 按文档约定触发退出。
- 会话停止是幂等操作，重复请求不重复清理、不产生 traceback。
- 把启动失败、停止原因和返回码明确传递给 CLI。

**验收标准：**

- `news chat --help` 和 `news chat` 可以工作。
- 不配置微信时可通过明确的配置选项运行纯本地模式（建议提供 `--no-wechat`），便于开发和测试。
- `/quit` 后输入线程、工作线程和已创建资源均能清理。
- Ctrl-C 和启动失败都能安全退出。

### CHAT-008：实现微信消息解析和长轮询适配器

**目的：** 接收 iLink 入站消息，并转换为统一 Chat 消息。

**实施内容：**

- 复用 `newsagent.wechat.ilink.ILinkClient.get_updates()`。
- 读取账号凭据和已绑定收件人；缺失时给出明确错误。
- 独立循环执行长轮询，长轮询超时按无新消息处理。
- 把服务端返回的消息解析为统一消息模型；只处理允许的个人文本入站消息。
- 按绑定收件人及真实协议字段校验发送方；拒绝不支持的群消息、非文本消息和 Bot 自身发出的消息。
- 提取可用的 message ID、文本和当前会话上下文令牌。
- 在实现前通过现有测试或真实账号诊断确认协议字段，避免基于猜测写死字段名。
- 关闭客户端或收到停止信号时，循环应可退出。

**验收标准：**

- mock 的 iLink 响应可以正确解析为 `ChatMessage`。
- 超时空响应不报成致命错误。
- 不符合来源或消息类型限制的消息不会进入处理队列。
- 不记录账号 token 或上下文令牌。

### CHAT-009：实现微信同步游标持久化和消息去重

**目的：** 降低重复处理和重启后消息丢失风险。

**实施内容：**

- 把同步游标保存在微信配置目录的独立状态文件内。
- 使用已有受保护文件写入能力，保证 POSIX 权限和原子替换。
- 启动时加载游标；收到服务端的新游标时按协议更新，包括无消息响应的情况。
- 维护最近已处理消息 ID，并定义有界的存储策略。
- 定义游标、消息入队和去重记录的顺序，避免简单地先推进游标再丢失未入队消息。
- 处理文件不存在、损坏和写入失败；不得悄悄覆盖不可解析状态。
- 如无法确保进程崩溃后无损恢复，应在文档中明确当前保证级别，并将持久化队列列为后续改进，而不是宣称严格 exactly-once。

**验收标准：**

- 游标可写入并在新实例中读回。
- 相同消息 ID 重复到达时，处理器仅接收一次。
- 文件写入失败可观察并有明确错误处理。
- 状态文件位于配置目录，不会意外被提交到版本控制。

### CHAT-010：实现微信输出适配器

**目的：** 通过已有 iLink 发送能力广播结果。

**实施内容：**

- 复用 `ILinkClient.send_text(recipient, text)`。
- 使用已绑定的接收人 ID，并在协议提供且仍有效时使用当前 `context_token`。
- 不在输出适配器里实现 LLM 或命令逻辑。
- 对超过微信单条限制的文本进行分段，限制分段大小并维持顺序。
- 区分临时网络错误、会话失效、未绑定及永久发送错误。
- 发送失败返回通道状态，不触发原业务命令重新执行。
- 关闭 iLink HTTP 客户端并释放资源。

**验收标准：**

- mock 可以校验目标收件人、上下文和发送文本。
- 长消息被正确分段。
- 发送异常只影响微信输出状态，不丢失终端输出。

### CHAT-011：把微信输入接入统一会话

**目的：** 完成微信与终端双入口的实际联通。

**实施内容：**

- 将微信适配器生成的消息推入 CHAT-007 的统一队列。
- 确保终端与微信输入经过同一个命令解析器和普通聊天处理器。
- 两类输入的每个结果都通过 CHAT-002 广播。
- 管理微信入站消息的上下文令牌与当前收件人状态，避免把旧上下文误用于新消息。
- 发送给微信的 Bot 自身消息不再次进入队列。
- 当微信暂时断网时，终端本地对话仍可工作；微信恢复后按既定重连策略继续接收。

**验收标准：**

- 终端普通文本和微信普通文本均调用同一个 LLM 服务。
- 终端与微信的命令均执行同一允许列表和处理函数。
- 不发生输出回环或同一消息重复处理。
- 微信故障不会导致本地会话整体退出。

### CHAT-012：完善错误处理、恢复和可观测性

**目的：** 保证常见故障下的行为可理解且受控。

**实施内容：**

- 区分启动失败、LLM 错误、命令错误、微信发送错误、微信登录失效和同步状态读写错误。
- 网络错误采用有上限的退避重试；禁止永久错误无限循环。
- 长耗时命令提供执行中提示或超时策略，避免用户误以为程序无响应。
- 输出通道记录独立结果；不得因为投递失败而重新执行命令。
- 日志记录消息来源、命令名、耗时与成功状态，不记录完整自由文本历史、token 或凭据。
- 关闭路径统一释放 HTTP 客户端、线程及其他资源。

**验收标准：**

- 对主要故障路径有自动化测试。
- 日志能区分通道失败和业务执行失败。
- 不能恢复的错误会明确显示给本地用户。

### CHAT-013：完成离线测试、回归和文档

**目的：** 为新会话功能建立稳定回归保障。

**实施内容：**

新增或完善测试，至少覆盖：

- 消息模型、空输入和非法来源；
- 普通聊天的 LLM 调用、上下文截断和 LLM 故障；
- 命令解析、引号参数、参数缺失、未知命令与危险命令拒绝；
- CLI 函数调用、stdout/stderr 捕获、返回码与异常处理；
- 广播两个通道、单端失败、长文本拆分和不产生回环；
- 同步游标恢复、消息 ID 去重、游标写入失败；
- `/quit`、Ctrl-C、EOF 和启动失败的资源清理；
