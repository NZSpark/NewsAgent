# News Chat 与命令支持设计

## 1. 目标与需求映射

本文依据 `doc/requirements.md`，设计统一的 `news chat` 交互入口，复用当前 NewsAgent 的新闻处理能力，使本地终端与微信 Bot 可以使用同一套对话和命令功能。

| 需求 | 设计方案 | 验收标准 |
|---|---|---|
| 与本地用户及微信 Bot 对话 | 建立统一 Chat 会话，由终端输入和微信消息共同驱动 | 两种来源均可发起对话 |
| 输入来自终端或微信 Bot | 通过终端输入线程和 iLink 长轮询接收消息 | 两个入口最终进入同一消息处理队列 |
| 输出同时发送给终端和微信 Bot | 统一输出广播器；普通回复、命令结果和错误信息共用广播路径 | 每次处理只生成一次结果，并分别尝试投递给两个输出端 |
| 普通文本转发给本地 LLM | 调用项目已有的统一 LLM 路由，沿用已有提供商配置与故障处理 | 收到自然语言问题后生成回复并广播 |
| 支持已实现的 `/` 命令 | 使用现有 CLI 参数定义和命令处理函数，增加允许列表 | 命令参数可用，执行结果广播到两个输出端 |
| `/quit` 退出 | 作为 Chat 会话内置控制命令 | 停止接收消息，清理资源并退出 |

## 2. 现有能力与复用边界

项目已有以下组件，可以直接复用：

- `src/newsagent/cli/main.py`：`build_parser()`、已有 `cmd_*` 处理函数以及新闻命令的参数定义。
- `src/newsagent/llm/client.py`：项目统一 LLM 调用、重试和提供商路由。
- `src/newsagent/agents/query.py`：`/ask` 所使用的本地新闻检索与问答逻辑。
- `src/newsagent/wechat/ilink.py`：`ILinkClient.get_updates()` 长轮询与 `send_text()` 文本发送。
- `src/newsagent/wechat/credentials.py`：微信账号、收件人和受保护状态文件的管理。
- `src/newsagent/wechat/config.py`：微信配置目录及配置读取。

不应重新实现新闻抓取、分类、聚类、排序、报告生成或 LLM 路由。Chat 只负责接收输入、分发任务、格式化结果和广播输出。

## 3. 总体架构

```text
                       news chat
                           |
                 +---------+---------+
                 |                   |
          本地终端输入           微信 iLink 长轮询
                 |                   |
                 +---------+---------+
                           |
                    消息接收队列
                           |
                    串行消息分发器
                           |
                +----------+----------+
                |                     |
          以 / 开头的命令           普通文本
                |                     |
         命令解析与允许列表       统一 LLM 路由
                |                     |
         复用现有 cmd_* 函数       生成回复
                |                     |
                +----------+----------+
                           |
                      结果格式化
                           |
                     输出广播器
                      /       \
                     /         \
                本地终端      微信 Bot
```

### 3.1 建议的模块划分

新增 `src/newsagent/chat/` 包：

| 模块 | 职责 |
|---|---|
| `chat/session.py` | 管理会话生命周期、输入队列、消息串行处理与 `/quit` |
| `chat/commands.py` | 解析斜杠命令、检查允许列表、调用现有 CLI 处理函数并捕获输出 |
| `chat/console.py` | 读取终端输入并提供终端输出接口 |
| `chat/wechat.py` | 长轮询、消息解析、同步游标持久化及微信发送 |
| `chat/broadcast.py` | 格式化统一回复，并向终端和微信端分别投递 |

可以根据实际实现规模合并模块，但应保持输入适配、命令分发和输出广播之间的职责边界。

在 `src/newsagent/cli/main.py` 的 `build_parser()` 中增加顶层命令 `chat`，绑定 `cmd_chat`。终端启动方式为：

```bash
news chat
```

开发环境也可以通过项目现有的 Python 模块入口启动：

```bash
python -m newsagent chat
```

## 4. 统一消息模型

不同输入端先转换成统一消息结构，再交给会话处理器：

```python
from dataclasses import dataclass
from typing import Literal

@dataclass(frozen=True)
class ChatMessage:
    source: Literal["console", "wechat"]
    text: str
    message_id: str | None = None
    sender_id: str | None = None
    context_token: str | None = None
```

实际实现可以补充接收时间、消息类型等字段，但不能把访问令牌或完整凭据放入通用消息日志。

消息处理顺序如下：

1. 验证文本非空并执行必要的长度限制。
2. 校验来源。微信输入只接受已绑定接收人对应的允许消息，拒绝不受支持的群消息、非文本消息或其他不符合协议的内容。
3. 微信消息使用消息 ID 去重，避免长轮询重试导致重复执行命令或重复生成回复。
4. 将消息放入统一队列。
5. 串行处理每条消息，确保 `/quit`、命令结果和对话回复具有确定顺序。
6. 通过统一输出接口广播结果。

消息结构中的具体字段应以现有 `ILinkClient.get_updates()` 实际返回的协议数据为准。在没有真实账号端到端验证前，不应将推测的协议字段名写死成未经检查的假设。

## 5. 本地终端与微信输入

### 5.1 本地终端

终端适配器逐行读取标准输入，每一行都是一条消息。空行可以忽略，普通文本和斜杠命令采用与微信端相同的处理流程。

输入读取和微信长轮询不能相互阻塞。建议为终端输入与微信接收分别设置工作线程，由统一队列协调消息处理。长耗时命令运行期间，应明确采用串行处理或任务队列策略，避免同时执行多个写数据库或报告生成任务。

### 5.2 微信 Bot

启动时读取：

- `news wechat login` 所保存的账号凭据；
- 已绑定的收件人 ID；
- 微信消息同步游标。

缺少必要凭据或绑定时，应输出明确错误并提示先完成 `news wechat login` 和 `news wechat bind`。不要打印 token、context token、二维码登录凭据或其他敏感数据。

接收线程通过 `ILinkClient.get_updates(sync_buf)` 长轮询：

1. 发送当前同步游标。
2. 解析响应并提取新消息。
3. 将合格的消息投递到统一输入队列。
4. 更新并持久化服务端返回的同步游标，即使本次没有消息也要按协议处理游标更新。
5. 发生暂时性网络错误时进行有上限的退避重试；登录失效或永久性错误应停止接收并通知会话处理器。

同步游标应放在微信配置目录中的独立状态文件内，通过现有受保护文件写入能力保存，并采用原子写入与限制访问权限的方式。不得把游标或账号凭据写到项目源码目录或普通日志。

**消息确认与去重必须协同设计。** 如果游标先持久化，而消息尚未安全进入可恢复的处理流程，进程崩溃可能使消息无法重放。首版至少应持久化游标、维护最近已处理消息 ID，并在同一进程内确保一条消息只触发一次处理；若需要严格的崩溃恢复语义，应进一步将消息接收、去重记录和处理状态存入持久化队列或数据库事务中。

## 6. 普通文本与本地 LLM

没有以 `/` 开头的文本视为自然语言对话，而不是 CLI 命令或 shell 命令。

处理流程：

1. 调用现有统一 LLM 接口 `newsagent.llm` 的生成能力。
2. 使用项目已有的提供商配置、重试及故障回退规则，不另起一套 API 密钥或模型配置。
3. 为对话设置明确的系统提示，说明这是 NewsAgent 助手、回答语言偏好、可用上下文及安全边界。
4. 将当前用户输入及必要的最近对话历史传给模型。
5. 提取模型回复文本，格式化后交给输出广播器。

普通聊天与 `/ask` 应区分：普通聊天面向一般对话，直接调用统一 LLM 路由；`/ask` 复用 `newsagent.agents.query.answer()`，基于本地新闻事件检索并作有来源约束的回答。

### 6.1 对话上下文

首版建议使用内存中的有限对话历史，例如最近 10 轮用户输入与助手回复。终端和微信共用该会话历史，因此两侧看到的是同一段对话。达到限制后删除较早的轮次，不无限增长上下文。

默认不持久化自由文本历史。进程重启后可以从空上下文开始；若未来增加持久化功能，需明确保存位置、保留期限与清理策略。

对话记录只作为模型上下文，不得被解释为系统指令。模型不得通过生成文本执行任意 shell 命令，也不能因为用户输入而自动运行未允许的 CLI 功能。

## 7. 斜杠命令解析与支持范围

### 7.1 通用规则

- `/` 后的第一个单词是命令名称，其余部分是参数。
- 通过 `shlex.split()` 解析命令行风格参数，因此含空格的参数可以使用引号，例如 `/search "人工智能 芯片"`。
- 命令名不区分大小写；参数值保持原样。
- `/quit` 是 Chat 内置命令，不转发给 CLI。
- 未知命令返回简明帮助，不送给 LLM 猜测执行。
- 普通文本中只有当第一个非空字符是 `/` 时才进入命令解析。以 `/` 开头的自然语言若要作为普通对话输入，应通过约定的转义方式处理，避免误执行。

### 7.2 首版命令允许列表

下表根据当前 `src/newsagent/cli/main.py` 中已注册的 CLI 功能规划。应以 `build_parser()` 实际注册的参数为准，在 Chat 中只暴露明确批准的命令。

| Chat 命令 | 转发行为 | 说明 |
|---|---|---|
| `/help` | Chat 内置 | 显示可用命令 |
| `/quit` | Chat 内置 | 结束整个 Chat 会话 |
| `/fetch [--source ID] [--limit N]` | `cmd_fetch` | 抓取信息源；`--source` 可重复 |
| `/sources` | `cmd_sources` | 查看信息源及状态 |
| `/recent [--hours N] [--limit N]` | `cmd_recent` | 查看近期事件 |
| `/search QUERY [--limit N]` | `cmd_search` | 检索本地新闻事件 |
| `/event EVENT_ID` | `cmd_event` | 查看单个事件 |
| `/health` | `cmd_health` | 检查信息源与 LLM 提供商健康状态 |
| `/pipeline [--limit N] [--hours N]` | `cmd_pipeline` | 执行分类、聚类与排序 |
| `/ask QUESTION` | `cmd_ask` | 基于本地事件问答 |
| `/semantic-cluster [--hours N]` | `cmd_semantic_cluster` | 语义聚类 |
| `/research [EVENT_ID] [--limit N] [--min-importance F] [--live]` | `cmd_research` | 研究指定事件或重点事件 |
| `/report [--hours N] [--formats md,html,pdf]` | `cmd_report` | 生成报告文件 |
| `/index [--limit N]` | `cmd_index` | 为事件和文章建立向量索引 |
| `/semantic-search QUERY [--limit N] [--articles]` | `cmd_semantic_search` | 语义搜索事件或文章 |

这里的命令名与参数源自现有 CLI，不代表所有功能都适合在每个部署环境默认开放。执行前还应检查参数、权限和副作用。

### 7.3 暴露边界

首版允许列表中不包括以下交互或敏感操作：

- `wechat login`：需要交互式扫码登录；
- `wechat bind`：会修改绑定关系；
- `wechat logout`：会清除凭据；
- `chat`：禁止递归启动另一个 Chat 会话；
- 任意 Python、shell、系统命令或未注册 CLI 命令。

`/report` 默认只生成报告。Chat 的广播器负责把命令结果发送给微信，因此不应默认再传入 `--send-wechat`，避免同一结果被重复发送。

### 7.4 推荐的分发方式

不要拼接 shell 字符串后交给 `subprocess(..., shell=True)`。应在进程内复用解析器与现有函数：

1. 从 `/` 命令中取得命令名和参数文本。
2. 用 `shlex.split()` 将参数转换为 token。
3. 检查命令名是否在允许列表中。
4. 用 `build_parser().parse_args([command_name, *tokens])` 复用 CLI 参数校验。
5. 确认解析得到的 `args.command` 在允许列表中，拒绝被禁止的子命令及副作用参数。
6. 用 `contextlib.redirect_stdout()` 和 `redirect_stderr()` 捕获命令输出，然后调用 `args.func(args)`。
7. 捕获参数错误、`SystemExit` 和普通异常，转换成可读结果并广播。

CLI 函数可能打印 JSON、文本或文件路径。输出捕获只用于把结果交给 Chat，不能改变已有命令函数的业务逻辑。实现时还要注意 stdout/stderr 是进程级全局对象；因此命令分发应串行执行，避免并发重定向互相干扰。

若后续发现某些命令难以安全地在当前进程中执行，可以为它们增加显式适配器；仍然不得使用未经限制的 shell 执行方式。

## 8. 输出广播与格式约定

所有处理结果统一表示为一个输出对象，例如：

```python
@dataclass(frozen=True)
class ChatOutput:
    text: str
    source: str
    is_error: bool = False
```

`source` 用于标识输出来自普通聊天、某条命令还是会话控制逻辑，主要供日志和诊断使用。

输出步骤：

1. 把命令捕获结果、LLM 回复或错误整理为文本。
2. 对空结果生成明确提示，而不是静默返回。
3. 检查字符长度；微信端以 `ILinkClient` 当前的消息长度限制为依据进行分段发送，不直接假定任意长字符串都能发送成功。
4. 向本地终端输出完整结果。
5. 向微信 Bot 发送同一结果的合适分段。
6. 分别记录两个输出端的成功或失败状态。

必须是**一次处理、两个输出端各自投递**，而不是把一条微信回复再当作新的输入消息送回处理器，否则会形成回环。

某一输出端失败时仍应尝试另一个输出端。例如，微信发送失败不能阻止本地终端显示命令结果。记录通道错误并提供必要提示；不要因为广播失败就重新执行已经完成的 `/fetch` 或 `/pipeline`，否则可能重复产生副作用。

命令输出可能包含长 JSON 或大量记录。首版应对终端保留可读完整结果，对微信端限制单条发送长度，并对超长结果提供分段或摘要策略。敏感数据不得因为转发结果而泄露。

## 9. 微信上下文、状态与资源清理

### 9.1 context token

微信回复应复用当前入站消息对应的 `context_token`（如果协议响应提供），并使用已绑定的收件人 ID。发送时向 `ILinkClient.send_text(recipient, text)` 传入必要上下文。

最新上下文应在合法入站消息到达时更新。状态更新需通过现有受保护的凭据管理能力写入，不在日志中输出 token。不能假定绑定时的 context token 永远有效。

### 9.2 会话状态

建议状态包括：

- `STARTING`：验证配置、账号和绑定；
- `RUNNING`：正常接收和分发消息；
- `STOPPING`：停止接受新任务并等待当前任务结束；
- `STOPPED`：关闭资源并退出。

只有一个会话控制器负责改变状态。重复的 `/quit` 应幂等，不可导致重复清理或 traceback。

### 9.3 `/quit` 与中断

收到 `/quit` 后：

1. 广播会话即将结束的消息；
2. 标记会话为停止状态，不再接收新的普通任务；
3. 尝试停止微信接收循环并等待工作线程结束；
4. 保存最新同步游标与必要状态；
5. 关闭 `ILinkClient` 的 HTTP 客户端和其他资源；
6. 返回正常退出码。

Ctrl-C 应进入同样的清理路径。终端 EOF 的行为应在实现中保持一致且有文档说明；推荐将其视为终端输入结束并触发优雅关闭，避免失去终端控制后留下持续运行的后台线程。

## 10. 错误处理与安全约束

- **凭据未就绪**：明确提示执行登录与绑定操作，不输出凭据内容。
- **微信长轮询超时**：按 `ILinkClient.get_updates()` 的现有语义视为无新消息，不应持续刷屏。
- **临时网络错误**：记录错误类型并退避重试；连续失败达到阈值后告知本地终端。
- **登录失效**：停止微信消息收发并提示重新登录；不可无限重试永久错误。
- **LLM 不可用**：给出清晰错误或现有统一路由提供的降级结果，同时继续保持会话可用。
- **未知命令/非法参数**：显示简洁用法，禁止执行。
- **命令异常**：捕获异常，保留必要诊断信息；不把凭据、环境变量或完整敏感请求输出给微信。
- **重复消息**：通过稳定消息 ID 去重，避免重发命令和重复生成结果。
- **消息回环**：只处理合法的用户入站消息，忽略 Bot 自身发送的消息和不受支持的消息类型。
- **资源泄漏**：无论正常退出还是异常退出，都必须关闭客户端并停止工作线程。

建议对 `/fetch`、`/pipeline`、`/report` 等较耗时或有副作用的命令设置执行超时或进度提示。若需要后台任务模式，应作为后续独立设计，不能在没有任务状态跟踪时误报成功。

## 11. 测试设计

测试必须默认离线运行，不依赖真实微信账号、真实 LLM 或外部网络。使用假的 LLM、假的输入端、假的广播器和 `ILinkClient` mock 覆盖以下场景。

| 测试范围 | 必测场景 |
|---|---|
| 普通消息 | 终端文本调用 LLM；微信文本调用相同服务；结果广播到两个输出端 |
| 双向一致性 | 来自任一端的结果同时尝试投递到终端和微信 |
| 命令解析 | `/recent` 默认参数、`/recent --hours 48`、引号包裹的 `/search` 参数 |
| 命令执行 | 允许命令转发到正确 `cmd_*`，返回 stdout/stderr 和退出状态 |
| 安全允许列表 | 未知命令、任意 shell 命令、`/wechat logout`、递归 `/chat` 被拒绝 |
| 错误处理 | argparse 参数错误、命令函数抛异常、LLM 异常、微信发送失败 |
| 消息去重 | 相同微信消息 ID 重复到达时只处理一次 |
| 游标持久化 | 游标更新、无消息响应、重启恢复和写文件失败 |
| 生命周期 | `/quit`、Ctrl-C、启动失败、长轮询失败后清理客户端 |
| 长消息 | 微信分段发送，分段失败时终端仍保留结果 |
| 不产生回环 | Bot 发送的自身消息不会再次触发 LLM 或 CLI 命令 |

端到端验收需要在完成微信登录及绑定后人工执行，不能用 mock 测试结果冒充真实协议验证。

## 12. 实施阶段

### 阶段 A：核心会话与本地终端

1. 新增 Chat 消息模型、统一队列、命令分发和输出广播。
2. 增加 `news chat` 命令。
3. 验证终端普通文本能够调用 LLM，命令能够复用现有 CLI 处理函数。
4. 验证 `/help`、未知命令与 `/quit`。

### 阶段 B：微信消息接入

1. 将 `ILinkClient.get_updates()` 接入微信输入适配器。
2. 处理同步游标、消息 ID 去重和 context token。
3. 将微信入站消息发送给统一队列。
4. 使用 `ILinkClient.send_text()` 实现广播器的微信输出端。
5. 验证错误恢复与资源清理。

### 阶段 C：命令覆盖和稳定性

1. 按允许列表逐个验证 `/fetch`、`/pipeline`、`/recent`、`/ask`、`/report` 等功能。
2. 覆盖长消息、命令错误、重发、网络故障和同时输入。
3. 执行完整离线测试与代码检查。
4. 通过人工微信账号进行端到端验收，记录协议实际行为。

## 13. 完成标准

功能完成需同时满足：

- `news chat` 可正常启动，并明确检查微信账号和绑定状态；
- 本地终端和微信 Bot 都可以发送普通消息及允许的 `/` 命令；
- 普通消息通过统一 LLM 路由生成回复；
- 已有新闻命令通过项目内函数执行，不通过 shell 拼接执行；
- 每个结果都向终端和微信两个输出端发起投递，并独立记录发送结果；
- `/quit` 可以安全结束会话并清理资源；
- 自动化测试覆盖消息处理、命令允许列表、去重、广播和退出；
- 完成一次真实微信消息收发验证。

本设计描述预期架构及实现方案，不表示上述 Chat 功能已经实现。真实 iLink 入站字段、同步游标恢复与微信端到端行为仍需通过当前项目代码和真实账号进一步确认。
