# 基于本地 LLM 的 AI 新闻 Agent 设计方案

为了在保障数据隐私的同时降低长期的 API 费用，我们可以设计一个基于本地开源大模型（Local LLM）的自动化资讯 Agent。以下是针对读取 `doc/sites.md` 资源的本地化处理方案。

## 1. 核心架构设计

系统主要由以下四个核心模块构成：

### 1.1 数据源与抓取模块 (Fetcher)
- **任务**：解析 `doc/sites.md` 列表，获取最新资讯正文。
- **技术栈**：
  - RSS 源解析：`feedparser`
  - 网页正文提取：`trafilatura` 或 `newspaper3k`（能够精准去除 HTML 广告和导航栏，提取纯文本，极大地节省本地 LLM 的 Context Token）。
  - 动态网页：使用 `Playwright` 渲染后抓取。

### 1.2 过滤与本地状态库 (State Manager)
- **任务**：历史记录去重，避免重复将旧新闻喂给本地 LLM 计算。
- **方案**：采用轻量级的本地 `SQLite` 或 `TinyDB`，基于 URL 和发布时间戳 (Hash) 记录已处理的文章。

### 1.3 本地 LLM 处理引擎 (Local LLM Engine)
- **任务**：总结长文、分类新闻类型、提取核心实体。
- **部署框架推荐**：
  - **Ollama**：部署极为简便，适合 macOS/Windows/Linux 环境，提供类似 OpenAI 的 API 接口。
  - **vLLM** / **Llama.cpp**：适合有独显的机器，提高推理吞吐量。
- **模型推荐**：
  - `Qwen-2.5 (7B/14B)`：中文理解和总结能力极为出色，适合消费级显卡。
  - `Llama-3.1 (8B)`：轻量且指令遵循好。
- **核心策略 (针对本地模型的优化)**：
  - **分块处理 (Chunking)**：本地模型上下文通常有限（如 8K），对于过长的文章必须先截断或分块总结 (Map-Reduce)。
  - **严格的 System Prompt**：控制输出格式（要求输出 JSON 或固定格式），避免本地小模型产生废话或“幻觉”。

### 1.4 聚合与分发模块 (Publisher)
- **任务**：整合总结结果并输出。
- **方案**：每日早晨自动生成 Markdown 格式的 Briefing 简报，并可通过 Webhook 推送至飞书、钉钉或 Telegram。

## 2. 自动化工作流 (Workflow)

1. **定时启动**：系统的 Cron Job 或 `APScheduler` 定时触发脚本。
2. **并发爬取**：异步请求 `doc/sites.md` 中的网址，提取最新 24 小时内的新闻网页正文。
3. **排队推理 (Producer-Consumer)**：将爬取到的纯文本放入队列。由于本地 GPU 算力有限，需单线程或按批次（Batch）将文章发送给本地 LLM 接口，逐步生成摘要。
4. **聚合报告**：等队列处理完毕后，执行一次整体的分类与排版，生成最终的 Markdown 文档。

## 3. 本地化落地的关键挑战与对策

- **算力瓶颈与耗时**：API 几乎是瞬时返回的，而本地推理单篇文章可能需要十几秒甚至更长。建议将**爬取**与**推理**解耦，爬取瞬间完成入库，后台通过后台服务慢慢消化库中的未总结新闻。
- **信息抽取准确度**：较小的本地模型可能会在总结长文时遗漏关键人名或公司名。应对方案是在提示词中明确要求“请提取文中提到的人物、公司名称以及核心事件”。
- **防爬虫穿透**：如果被目标网站封 IP，推荐在爬取阶段引入 `Jina Reader API` (https://r.jina.ai/) 作为中间层，直接获取干净的 Markdown，减轻本地算力和清洗逻辑的压力。
