# 新闻简报多格式输出增强方案

## 1. 背景与目标

当前报告功能位于 `src/newsagent/agents/report.py`，主要通过 `build_report()` 从 SQLite 查询指定时间范围内的事件，生成 Markdown 字符串，再由 `write_report()` 写入 `output/`。CLI 在 `src/newsagent/cli/main.py` 中通过 `news report --hours H` 调用报告生成逻辑。

目前实现只提供 Markdown 文件输出。本方案将报告输出扩展为 **Markdown（`.md`）、HTML（`.html`）和 PDF（`.pdf`）三种格式**，并允许一次运行同时生成多个格式。

### 目标

1. 保留现有新闻筛选、事件排序、头条选择和报告内容，不因格式变化而产生不同的数据口径。
2. 支持单独生成一种格式，也支持一次生成全部三种格式。
3. 默认行为保持兼容：不指定格式时仍只生成 Markdown。
4. 为 HTML 提供可读的网页样式，为 PDF 提供适合打印、分页与中文阅读的版式。
5. 将格式渲染与数据库查询、业务逻辑分离，便于未来增加其他输出格式。
6. 不要求 PDF 或 HTML 功能的依赖成为基本采集、分类、查询等功能的强制依赖。
7. 所有报告继续保存到本地 `output/` 目录，不增加网络服务或在线转换服务的依赖。

### 非目标

本阶段不开发 Web 服务、不改变事件聚类与重要性评分算法、不要求浏览器在线访问才能阅读生成的文件，也不在报告生成期间重新调用 LLM。报告继续使用数据库中已有的事件摘要与分析字段。

## 2. 推荐方案

采用 **统一报告数据模型 + 三个独立渲染器** 的设计。

```text
news report --hours 24 --formats md,html,pdf
                     |
                     v
              查询 SQLite 事件
                     |
                     v
             统一 ReportData
                     |
          +----------+----------+
          |          |          |
          v          v          v
     Markdown      HTML       HTML + CSS
     Renderer    Renderer         |
          |          |             v
          v          v       PDF Renderer
        .md        .html         .pdf
          |          |             |
          +----------+-------------+
                     v
                output/
```

同一批事件数据只查询一次，随后交由不同渲染器生成文件。HTML 是独立输出格式；PDF 推荐基于相同的 HTML 模板与样式生成，以减少两套版式重复维护造成的不一致。

### PDF 技术选择

首选 **WeasyPrint**，将 HTML 和 CSS 渲染为 PDF。它适合报告类文档，可利用 HTML 模板构建标题、链接、表格、页眉页脚与分页样式。应将相关 Python 依赖放入可选的 PDF 依赖组，而不是基础依赖。

实施前需要在目标 macOS、Linux 或 Windows 环境验证 WeasyPrint 所需的系统库与字体配置。尤其要验证中文字体、换页、超长标题、URL、代码及特殊字符的显示。WeasyPrint 并不意味着在所有操作系统上无需额外安装即可运行。

不建议第一阶段引入远程 PDF 转换服务，也不建议依赖需要单独下载浏览器的大型浏览器自动化流程作为默认 PDF 引擎。若部署环境无法满足 WeasyPrint 的系统依赖，应在实施前评估备用渲染引擎，而不是在生成失败时静默输出损坏文件。

## 3. CLI 设计

### 3.1 新参数

扩展当前 `news report` 命令，增加 `--formats` 参数。

```bash
# 默认行为不变，只生成 Markdown
news report --hours 24

# 只生成 HTML
news report --hours 24 --formats html

# 只生成 PDF
news report --hours 24 --formats pdf

# 一次生成全部三种格式
news report --hours 24 --formats md,html,pdf

# 生成最近七天范围的全部格式
news report --hours 168 --formats md,html,pdf
```

建议约定如下：

- `--hours H`：保持现有含义与默认值 24。
- `--formats`：逗号分隔的格式列表，允许 `md`、`html`、`pdf`；未指定时默认为 `md`。
- 格式名称大小写不敏感；解析后统一为小写并去重。
- 传入未知格式时，应返回清晰的参数错误，并列出支持的格式。
- 若请求 PDF 而 PDF 依赖未安装，应报告如何安装可选依赖，不应静默跳过 PDF。
- 格式列表的解析与参数校验在 CLI/格式分发层完成，渲染器不应各自解析命令行参数。

逗号分隔的接口便于在一次命令中明确表示所需输出，也易于以后增加格式。第一阶段不必同时引入别名、复杂模板参数或任意输出路径参数。

### 3.2 返回值与命令行输出

现有 `write_report()` 返回单个 `Path`，且测试直接调用 `build_report()` 并检查 Markdown 字符串。为控制兼容性影响，建议：

- 保留 `build_report(hours, top_n)` 作为 Markdown 字符串生成入口，继续满足现有调用方与测试的预期。
- 保留 `write_report(hours, out_dir)` 的现有默认语义，仍只生成 Markdown 并返回 `Path`。
- 新增统一入口，例如 `write_reports(hours, formats, out_dir)`，返回按格式组织的输出路径集合，由 CLI 使用。
- 当只生成一种格式且为默认 Markdown 时，CLI 继续输出原来的单个文件路径；需要多个格式时，输出 JSON 映射，例如 `{"md":"output/daily_2026-10-10.md","html":"output/daily_2026-10-10.html","pdf":"output/daily_2026-10-10.pdf"}`。

具体 API 名称可以在实现时按代码风格调整，但应避免无必要地破坏现有 Python 调用方式。

## 4. 统一报告数据模型

将数据库读取从 Markdown 字符串拼接逻辑中拆分出来。建议新增 `ReportData` 数据结构，至少包含：

- `title`：报告标题，例如 `AI 日报 · 2026-10-10`。
- `generated_at`：报告生成时间，统一使用明确的时区语义。
- `period_hours`：本报告覆盖的小时数。
- `events_count`：选中的事件数量。
- `top_events`：头条事件列表。
- `other_events`：其他事件列表。
- `events`：如实现需要，也可保留完整的有序事件列表。

每个事件至少应提供 `event_id`、`title`、`summary`、`why_it_matters` 和 `base_score` 等现有报告使用的字段。数据结构只负责承载已查询的信息，不负责 HTML 转义、CSS、PDF 分页或文件写入。

推荐模块拆分：

```text
src/newsagent/agents/
├── report.py              # 查询和编排；保留现有公开入口
└── report_renderers/
    ├── __init__.py
    ├── markdown.py        # Markdown 渲染
    ├── html.py            # HTML 模板与网页样式
    └── pdf.py             # PDF 生成、字体与分页设置
```

如果早期实现规模较小，也可以先在 `report.py` 中使用独立函数组织三个渲染器；但数据查询、渲染和文件写入仍应有明确边界，后续再按模块拆分。

## 5. 三种格式的设计要求

### 5.1 Markdown（MD）

- 作为现有格式保留，默认输出格式不变。
- 保留当前中文标题、覆盖时间、事件总数、头条与其他事件结构。
- 保留摘要、影响说明和评分字段的现有显示规则。
- 无事件时继续输出可读的空报告提示。
- 使用 UTF-8 编码写入，不额外引入渲染依赖。

### 5.2 HTML

建议采用完整的 HTML5 文档，而不只是把 Markdown 原文包裹在 `<pre>` 标签中。

内容建议包括：

- 文档标题和生成时间。
- 报告覆盖的时间窗口与事件总数。
- 头条事件区域。
- 其他事件列表。
- 事件摘要、影响说明及评分。
- 清晰的来源链接（仅当报告数据中确实包含可靠的文章 URL 时添加）。

样式要求：

- 页面主体宽度适中、字体层级清晰，支持桌面和移动设备阅读。
- 使用 CSS 定义标题、正文、事件分组、链接和打印布局。
- 提供浅色、简洁、适合长文阅读的默认主题，避免依赖外部 CDN、在线字体或远程图片。
- 使用正确的 UTF-8 声明，并设置适当的中文字体回退栈。
- 对事件标题、摘要、影响说明和 URL 等所有外部或数据库文本进行安全转义；不要把新闻正文直接插入未经转义的 HTML。
- 为打印样式提供 `@media print` 规则，使内容在打印或转换成 PDF 时保持合理的留白与分页。

可以使用内置 HTML 生成逻辑，也可以采用 Jinja2 模板。如果采用模板，应对用户数据进行自动转义，并避免使用不必要的复杂模板依赖。

### 5.3 PDF

PDF 的主要目标是获得可以保存、打印和分享的稳定文档。

建议的版式：

- A4 纸张，明确页边距。
- 首页显示报告标题、日期、统计信息和头条新闻。
- 事件标题与正文尽量保持在同一页，避免标题孤立在页尾。
- 为较长事件设置合理的分页规则，允许长内容跨页。
- 页脚显示页码；必要时显示报告日期。
- 链接在 PDF 中保留可点击性（由渲染引擎支持时启用）。
- 对中文文本选择已安装且可嵌入的字体，防止中文显示为空白方框或丢失字形。
- 明确处理长标题、长 URL、emoji、特殊符号和空内容。

CSS 可以采用 `@page`、`break-before`、`break-after`、`break-inside` 等打印规则。应避免简单地对所有事件使用 `break-inside: avoid`，否则较长事件可能导致分页布局异常。

PDF 生成失败时，应显示错误原因并返回非零状态。多格式任务是否继续输出其他格式，需要采用明确策略；推荐独立格式生成、收集错误并继续处理剩余格式，最后返回部分失败状态，防止一个 PDF 依赖问题阻止 MD 与 HTML 生成。

## 6. 文件命名与输出目录

默认沿用现有 `output/` 目录以及日报、周报的命名规则：

| 格式 | 日报示例 | 周报示例 |
| --- | --- | --- |
| Markdown | `output/daily_2026-10-10.md` | `output/weekly_2026-10-10.md` |
| HTML | `output/daily_2026-10-10.html` | `output/weekly_2026-10-10.html` |
| PDF | `output/daily_2026-10-10.pdf` | `output/weekly_2026-10-10.pdf` |

日期取报告生成时的日期。小时数不超过 24 时沿用 `daily` 前缀，大于 24 时沿用 `weekly` 前缀，以保持当前行为。将来如需生成任意小时范围对应的正式报告类型，可以另行定义更精细的命名规则，本阶段不改变现有逻辑。

多格式输出应基于同一次查询、同一个生成时间和同一组事件，避免同一批输出文件之间出现数量、排序或标题不一致。写入时应使用 UTF-8（文本格式）或二进制文件模式（PDF），并确保输出目录存在。

可进一步考虑先写入临时文件，确认渲染成功后再原子替换目标文件，避免中断时覆盖出半成品文件。该机制不是第一阶段的强制条件，但 PDF 文件生成建议优先采用。

## 7. 依赖管理与配置

当前 `pyproject.toml` 中没有 HTML/PDF 专用依赖。推荐采用可选依赖组，避免所有用户安装项目时都必须具备 PDF 渲染环境。

设计示例（版本号应在实施时结合项目环境验证后确定）：

```toml
[project.optional-dependencies]
dev = ["pytest>=8.0", "pytest-asyncio>=0.24"]
html = ["Jinja2>=3.1"]
pdf = ["WeasyPrint"]
all-reports = ["Jinja2>=3.1", "WeasyPrint"]
```

如果 HTML 使用标准库即可满足需求，就不必增加 `html` 依赖组。若 PDF 依赖已经包含 HTML 模板引擎，可以在 `all-reports` 中统一声明，避免重复或冲突的依赖定义。

安装方式建议：

```bash
# 只使用 Markdown：无需额外安装格式依赖
.venv/bin/python -m pip install -e ".[dev]"

# HTML 模板（仅在选用 Jinja2 时需要）
.venv/bin/python -m pip install -e ".[html]"

# PDF 与 HTML 模板
.venv/bin/python -m pip install -e ".[all-reports]"
```

以上是方案示例，不代表这些可选依赖已经加入或验证通过。实施时应检查项目的 Python 版本约束、WeasyPrint 系统依赖、中文字体和跨平台安装说明，并根据实际选型调整依赖组。

## 8. 错误处理与运行行为

需要明确处理以下情况：

1. **格式名称非法：** 在开始查询数据库或写文件之前拒绝请求，并列出合法格式。
2. **PDF 依赖缺失：** 给出安装提示，不能静默跳过请求的 PDF。
3. **无事件：** 三种格式都应该正常输出空报告，说明数据为空以及下一步可执行的采集/处理命令。
4. **HTML 模板或 CSS 异常：** 记录具体格式的失败信息，不应误报该格式成功。
5. **PDF 字体或系统库缺失：** 明确指出依赖、字体或系统库问题，便于用户排错。
6. **输出目录不可写：** 返回明确路径和系统错误。
7. **多格式部分失败：** 已成功生成的文件仍可保留；命令应报告所有成功路径与失败格式，并通过非零退出码表示本次请求未全部成功。
8. **覆盖同名文件：** 沿用现有行为，明确新报告会覆盖同日期、同类型的旧报告；若以后需要保留历史版本，应另行设计归档策略。

生成格式不应触发新闻重新抓取。除非用户显式执行抓取或带有实时 fallback 的研究命令，报告输出模块只读取现有数据并进行本地渲染。

## 9. 测试方案

测试以本地、离线、确定性测试为主，不需要访问新闻站点或调用真实 LLM Provider。

### 9.1 单元测试

- 同一份 ReportData 可生成 Markdown、HTML 和 PDF 输出。
- Markdown 的现有标题、事件排序、头条选择与空报告行为保持一致。
- HTML 文档包含正确的 UTF-8 声明、标题、正文内容与打印样式。
- HTML 渲染对 `<script>`、`<`、`&`、引号等恶意或特殊文本进行正确转义。
- PDF 在安装依赖的环境中生成非空文件，并检查 PDF 签名或使用可用解析器确认文件结构有效。
- 无事件情况下三种格式都能生成可读输出。
- 不同格式生成的日期、时间范围、事件顺序及事件数量一致。
- 未知格式、缺少 PDF 依赖、输出目录权限不足等情况有可测试的错误路径。

### 9.2 CLI 测试

- `news report --hours 24` 仍只生成 Markdown。
- `--formats html` 和 `--formats pdf` 分别只生成对应文件。
- `--formats md,html,pdf` 生成三个文件。
- 不合法格式应得到非零退出码和可理解的提示。
- 多格式中单一格式失败时，其他可生成格式仍能完成，且最终结果明确标识部分失败。

### 9.3 PDF 集成测试

PDF 集成测试应在安装对应可选依赖的环境中运行，并尽可能使用本地字体或测试夹具。至少验证：

- 中文字符可正确渲染。
- 长标题和长正文可以正常分页。
- 空报告不会产生损坏 PDF。
- 输出具有合理的页面尺寸与页边距。
- HTML/CSS 模板更新不会破坏 PDF 渲染。

这些是实施后应执行的测试要求，不表示当前功能已经完成测试。

## 10. 分阶段实施计划

### 阶段一：拆分报告数据与 Markdown 渲染

1. 保留现有 `build_report()` 行为。
2. 提取统一数据查询与 ReportData 结构。
3. 将现有 Markdown 字符串构建逻辑独立为 Markdown Renderer。
4. 为现有报告测试补充数据一致性检查。

**验收标准：** 默认 Markdown 输出行为不变，现有测试通过，不触发联网请求。

### 阶段二：新增 HTML 输出

1. 添加 HTML Renderer 和模板/CSS。
2. 实现 UTF-8、中文字体回退、响应式布局与打印样式。
3. 添加 `--formats` 参数和 HTML 文件写入逻辑。
4. 增加 HTML 转义、空数据和 CLI 测试。

**验收标准：** 可单独生成完整 HTML 报告；Markdown 默认行为保持兼容。

### 阶段三：新增 PDF 输出

1. 选定并配置 PDF 引擎及可选依赖组。
2. 使用同一 HTML 模板生成 PDF。
3. 加入中文字体、分页、页码和长内容处理。
4. 加入缺失依赖检测与可读的错误提示。
5. 编写 PDF 单元与集成测试。

**验收标准：** 在声明支持的环境中可稳定生成中文 PDF，依赖缺失时不会静默失败。

### 阶段四：多格式编排与文档完善

1. 完成 `--formats md,html,pdf` 的多格式生成。
2. 统一文件命名、时间戳和输出路径报告。
3. 实现多格式部分失败的错误汇总与退出码。
4. 更新 README、安装说明与排错文档。

**验收标准：** 一条命令可生成三种一致的报告文件；只生成 Markdown 的原有调用方式继续可用。

## 11. 风险与注意事项

| 风险 | 应对措施 |
| --- | --- |
| WeasyPrint 安装涉及系统库 | 将其设为可选依赖，记录各平台安装与排错步骤 |
| 中文字体缺失或未嵌入 | 明确字体回退、字体安装及 PDF 渲染测试要求 |
| HTML 注入风险 | 使用模板自动转义或显式 HTML 转义，不拼接未经转义的事件内容 |
| 三种格式出现内容不一致 | 统一 ReportData、查询一次、共用生成时间与事件顺序 |
| PDF 布局受 CSS 更新影响 | 将 HTML 与 PDF 样式一起进行回归测试 |
| 可选依赖影响现有安装 | 将 HTML/PDF 依赖从核心依赖中分离 |
| 报告生成意外触发网络访问 | 输出阶段只使用本地数据，不调用抓取器或 LLM |

## 12. 最终建议

采用统一报告数据模型、Markdown/HTML/PDF 独立渲染器，以及可选 PDF 依赖的方案。先把现有 Markdown 生成逻辑抽取为稳定的公共数据与渲染接口，再添加 HTML，最后基于 HTML/CSS 增加 PDF。

保留 `news report --hours 24` 只生成 Markdown 的现有默认行为，通过 `--formats md,html,pdf` 明确请求多格式输出。这样能够兼顾兼容性、依赖管理、离线渲染和后续扩展，也能让三种格式在数据内容上保持一致。
