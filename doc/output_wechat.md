# NewsAgent 微信报告输出功能设计文档

> 文档状态：需求与技术设计基线  
> 适用项目：NewsAgent  
> 目标：将 NewsAgent 已经生成的新闻报告发送到指定的个人微信，支持手动发送和操作系统定时推送。  
> 设计原则：复用现有报告生成能力；独立实现微信发送；不依赖 Hermes 或 OpenClaw Gateway；使用系统调度器；重要运行行为可配置、可追踪、可测试。

## 1. 背景与目标

NewsAgent 已具备新闻报告生成能力，包括 PDF 输出。本功能在现有报告流程之上增加微信输出能力，使用户能够通过命令行发送已生成的报告，也可以使用 macOS `launchd`、Linux `cron` 等操作系统定时机制定期推送报告。

设计以复用 Hermes 的 Python 微信实现为主要参考，选择性移植与 iLink Bot 协议、二维码登录、消息收发和上下文管理有关的必要实现，而不是将 Hermes 或 OpenClaw 作为外部运行依赖。

### 1.1 目标

- 通过二维码完成微信 iLink Bot 登录。
- 将一个个人微信账号绑定为唯一固定收件人。
- 支持手动发送和系统定时推送。
- 支持摘要、完整报告文本、摘要加 PDF 三种发送模式。
- 复用 NewsAgent 已有报告与 PDF 文件，不在微信发送模块内重新生成报告或 PDF。
- 支持发送最新报告，也允许手动指定报告文件。
- 支持可配置的发送重试策略，并记录发送结果。
- 提供操作系统定时任务模板和安装说明，不自动修改用户的系统配置。

### 1.2 不在本功能范围内

- 微信群消息、群聊机器人和多个收件人管理。
- 运行 Hermes Gateway 或 OpenClaw Gateway。
- 增加 NewsAgent 内部常驻调度服务。
- 在发送模块里重新调用 LLM 生成摘要。
- 在发送模块里生成或补生成 PDF。
- 自动修改系统 `launchd` 或 `cron` 配置。
- 完整的微信聊天机器人交互能力。微信入站消息仅用于首次收件人绑定，以及协议所必需的上下文维护。

## 2. 已确认的需求与默认决策

| 项目 | 确定方案 |
| --- | --- |
| 微信集成方式 | 将 Hermes 的必要 Python 实现选择性移植到 NewsAgent |
| 运行依赖 | 独立运行，不要求启动 Hermes 或 OpenClaw Gateway |
| 微信接入 | 使用微信 iLink Bot 接口；具体协议细节以移植时验证的接口版本为准 |
| 登录 | NewsAgent 内置二维码登录流程 |
| 凭据保护 | 保存至 NewsAgent 自己的配置目录，并限制文件访问权限 |
| 收件人 | 固定为一个个人微信账号，不支持群聊或多收件人 |
| 首次绑定 | 扫码登录后，由收件人主动向 Bot 发消息，程序据此记录收件人标识和必要上下文 |
| 手动发送 | 提供独立命令，也支持现有报告命令附带发送选项 |
| 定时推送 | 由操作系统调度器负责，不增加内部常驻调度器 |
| 定时任务模板 | 提供模板和文档，由用户自行安装，不自动修改系统配置 |
| 定时频率 | 每天指定一个固定时间 |
| 定时使用的时区 | 运行机器的本地时区；夏令时由操作系统处理 |
| 定时执行方式 | 支持生成报告后发送，以及发送已有报告 |
| 生成失败 | 停止本次发送，记录错误；不回退发送旧报告 |
| 发送模式 | 摘要、完整报告文本、摘要加 PDF |
| 全局默认模式 | 摘要加 PDF |
| 定时任务默认模式 | 默认继承全局默认模式，可单独覆盖 |
| 摘要来源 | 复用已生成报告中的摘要，不重新调用 LLM |
| PDF 来源 | 复用 NewsAgent 已生成的 PDF |
| 缺少 PDF | 停止发送并记录错误，不补生成 PDF，不降级为摘要模式 |
| 手动报告选择 | 默认使用最新报告，也支持指定单个报告文件 |
| 摘要加 PDF 的文件选择 | 指定 PDF 文件，由程序定位同一报告的摘要文件 |
| 发送失败重试 | 默认最多重试 3 次，重试间隔 10 秒；参数可以修改 |

如果实现中发现 iLink 协议的实际限制与上述目标冲突，应明确记录具体限制和影响，不应通过静默降级或隐式替换行为掩盖问题。

## 3. 技术方案比较

### 3.1 Hermes

参考文档：[Hermes 微信接入文档](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/weixin)

Hermes 提供 Python 微信接入实现，可作为 iLink Bot 登录、二维码认证、消息收发、轮询、上下文管理和消息分段的主要参考。本项目不安装或运行完整 Hermes 服务，而是从可复用实现中提取必要逻辑，并使其适配 NewsAgent 的配置、命令行、报告文件和日志体系。

复用时应当：

- 明确所参考的 Hermes 代码版本和具体源文件。
- 只移植 NewsAgent 实际需要的协议与传输逻辑，不复制与代理对话、工具执行等无关能力。
- 将协议层与 NewsAgent 报告业务解耦。
- 检查第三方依赖的许可证、版本兼容性和安全状态。
- 按原项目许可证保留相应版权声明和许可证文件，并记录实质性修改。
- 不假设 Hermes 的内部路径、配置格式或会话管理可以直接作为 NewsAgent 的公共接口。

### 3.2 OpenClaw

参考文档：[OpenClaw 微信接入文档](https://docs.openclaw.ai/zh-CN/channels/wechat)

OpenClaw 的微信接入实现可作为协议行为、二维码流程和消息处理的补充参考。不过其微信插件主要属于 TypeScript/Node.js 生态，面向 OpenClaw 插件运行环境，不适合直接作为 Python NewsAgent 的运行依赖。

本方案不要求安装 OpenClaw，也不把 OpenClaw Gateway 作为消息中转服务。若参考其源代码，应另行审查对应许可证、依赖及代码复用条件。

### 3.3 最终选择

优先选择 Hermes Python 实现作为移植基础；OpenClaw 只作为比较与交叉验证来源。最终模块由 NewsAgent 直接调用 iLink Bot 接口。

## 4. 总体架构

```text
手动 CLI 或操作系统定时任务
              |
              v
       NewsAgent CLI
              |
              v
       微信发送服务层
              |
       +------+------+
       |             |
       v             v
 报告文件解析器   微信账号与收件人状态
       |             |
       v             v
 摘要/正文/PDF   iLink Bot 客户端
       |             |
       +------+------+
              |
              v
       消息发送与重试
              |
              v
       微信 iLink Bot API
              |
              v
       固定个人微信收件人
```

定时推送由操作系统负责启动 NewsAgent CLI。运行完成后，CLI 进程退出；程序不需要为了定时发送长期驻留在后台。

### 4.1 建议模块边界

建议根据现有项目的包结构安排下列职责，具体文件路径以实施时与实际代码结构对齐为准。

| 模块职责 | 主要任务 |
| --- | --- |
| WeChat 配置与状态 | 读取配置、定位凭据、保存收件人绑定和发送状态 |
| 二维码认证 | 请求登录二维码、显示二维码、轮询登录状态、保存认证结果 |
| iLink 客户端 | 实现必要的认证、请求、轮询和发送协议 |
| 收件人绑定 | 获取入站消息中的收件人标识及必要上下文，绑定唯一收件人 |
| 报告解析器 | 查找已生成的摘要、正文和 PDF，检查报告对应关系 |
| 发送服务 | 根据发送模式构建消息、拆分长文本、协调附件发送 |
| 重试与日志 | 判断是否重试，记录结果，保存失败诊断信息 |
| CLI 命令 | 暴露登录、状态、发送、解绑等用户操作 |
| 定时任务模板 | 提供系统调度配置、命令示例、运行环境与日志路径说明 |

协议客户端不应直接负责寻找 NewsAgent 的报告文件；报告解析器也不应直接访问 iLink API。这样可以独立测试报告选择、格式转换和网络传输。

## 5. 微信登录与收件人绑定

### 5.1 登录与绑定是两个不同步骤

扫码登录认证的是 iLink Bot 身份，不能把它直接当作接收报告的个人微信账号。程序必须独立保存 Bot 登录凭据，以及被绑定的个人收件人标识。

### 5.2 首次初始化流程

1. 用户执行 `news wechat login`。
2. NewsAgent 请求 iLink 登录二维码，并在终端显示二维码或相应扫码提示。
3. 用户用微信扫码，并按微信客户端提示完成授权。
4. NewsAgent 完成登录状态确认，将 Bot 账号需要的认证凭据保存至本地受保护目录。
5. NewsAgent 提示用户使用目标个人微信向该 Bot 主动发送一条消息。
6. 程序接收该入站消息，获取协议提供的收件人标识以及发送后续消息所需的上下文信息。
7. 用户确认绑定后，程序保存唯一收件人记录并显示绑定状态。首次绑定完成后，不再需要每次发送时重新选联系人。
8. 程序执行必要的协议检查；若当前账号、收件人信息或上下文不满足主动发送条件，应明确提示错误，不得显示虚假的绑定成功状态。

首次绑定默认只接受一个收件人。已有绑定时，不应由其他入站用户静默覆盖。重新绑定必须通过明确的解绑或重新绑定操作完成。

### 5.3 后续发送

后续手动发送和定时推送都使用已保存的收件人标识。若 iLink 协议要求发送请求携带上下文令牌或类似字段，客户端应按协议正确保存、更新和使用这些字段，不得将临时上下文误当成永久凭据。

程序应检测认证失效、收件人绑定缺失、上下文失效等情况，并返回可操作的错误信息。若重新授权或重新绑定是必要条件，应要求用户手动处理。

### 5.4 登录、解绑和状态命令

建议提供以下操作：

- `news wechat login`：进行扫码登录及首次绑定引导。
- `news wechat status`：显示账号登录状态、收件人是否绑定、全局默认发送模式和必要配置摘要；不输出敏感令牌。
- `news wechat bind`：在明确确认后绑定或重新绑定个人收件人。
- `news wechat logout`：清除本地微信登录凭据和绑定状态；必要时保留已生成的报告及普通日志。

具体命令名称可以在实施时与现有 CLI 风格统一，但以上操作应具备相同语义。

## 6. 凭据与配置存储

### 6.1 存储原则

凭据保存在 NewsAgent 自己的配置目录，不依赖 Hermes 的 `~/.hermes` 路径，也不要求用户配置 macOS Keychain 或 Linux Secret Service。

若项目已经定义统一配置目录，优先在其下创建独立的微信子目录；否则使用符合平台习惯的用户级配置目录。建议目录布局如下：

```text
<NewsAgent 用户配置目录>/wechat/
├── config.json          # 非敏感配置
├── account.json         # Bot 登录凭据
├── recipient.json       # 唯一收件人和必要协议上下文
├── delivery-state.json  # 必要的发送状态或去重记录
└── logs/                # 如项目选择在该目录存放专项日志
```

不要把真实令牌或个人收件人标识提交到 Git，也不要将其放入示例配置文件。

### 6.2 文件权限

在支持 POSIX 权限的系统中：

- 微信专用配置目录建议设置为 `0700`。
- 包含凭据、收件人标识或上下文令牌的文件建议设置为 `0600`。
- 写入凭据时优先采用安全的临时文件写入和原子替换，避免异常退出导致状态文件损坏。
- 检测到权限明显过宽时，应至少发出警告；不能安全写入凭据时，应明确失败。
- 在 Windows 等使用不同权限模型的平台，应采用该平台的等效访问控制，并在文档中说明限制。

配置和状态文件应支持损坏检测。程序不得静默覆盖无法解析的凭据文件；应提示用户备份或重新登录。

### 6.3 配置示例

下例只展示非敏感配置。实际凭据不应写入该文件。

```json
{
  "wechat": {
    "enabled": true,
    "default_mode": "summary_pdf",
    "retry": {
      "max_retries": 3,
      "interval_seconds": 10
    },
    "message": {
      "split_long_text": true
    },
    "schedule": {
      "daily_time": "08:00",
      "mode": null,
      "action": "generate_and_send"
    }
  }
}
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `enabled` | 是否允许通过 CLI 发送微信 |
| `default_mode` | 全局默认模式，默认 `summary_pdf` |
| `retry.max_retries` | 首次发送以外的最大重试次数 |
| `retry.interval_seconds` | 每次失败后的默认等待秒数 |
| `message.split_long_text` | 是否按接口限制拆分较长文本 |
| `schedule.daily_time` | 每日定时推送的本地时间，用于生成调度模板或供用户参考 |
| `schedule.mode` | 定时发送模式；`null` 表示继承全局默认值 |
| `schedule.action` | 定时任务操作：生成报告后发送，或发送已有报告 |

这份配置不会启动内部调度器。系统定时任务仍由用户安装的 `launchd` 或 `cron` 项目触发。

建议只在一个地方维护权威配置，避免 CLI 配置、系统定时模板和发送脚本之间出现相互冲突的默认值。真实收件人和凭据状态应与普通配置分开管理。

## 7. 报告输入和选择规则

### 7.1 发送模块只消费已生成文件

微信发送服务本身不生成新闻报告、不生成摘要，也不生成 PDF。它只负责查找、验证、读取和发送现有报告文件。

对于定时任务，若用户选择先生成报告再发送，则由操作系统调度的 NewsAgent 报告命令先运行现有报告生成流程；只有生成命令成功后，才执行发送步骤。

### 7.2 默认选择最新报告

手动发送未指定文件时，默认选择最新一次成功生成的报告。报告选择应使用 NewsAgent 能提供的生成元数据或稳定的文件命名约定，确保同一报告的摘要、正文和 PDF 对应一致。

如果存在可靠的报告清单或元数据，优先根据清单判断一组报告文件是否齐全；不要仅凭不同文件的修改时间，随意把不同批次的摘要与 PDF 拼成一组。

若无法确定哪份报告最新，或对应文件不齐全，程序应停止发送并说明原因，而不是猜测一个文件。

### 7.3 手动指定文件

通过 `--file PATH` 指定报告文件。文件含义取决于发送模式：

| 模式 | `--file` 指定的文件 |
| --- | --- |
| `summary` | 已生成的摘要文本文件 |
| `full` | 已生成的完整报告文本文件，例如 Markdown 或纯文本 |
| `summary_pdf` | 已生成的 PDF 文件；程序据此定位同一份报告的摘要文件 |

指定路径时应检查文件是否存在、可读、格式受支持。绝对路径和相对路径的解析规则应与现有 CLI 一致。不要在不明确时默默转换、覆盖或重新生成用户文件。

### 7.4 摘要加 PDF 的配对规则

指定 PDF 后，报告解析器应通过稳定的报告标识、清单记录或约定的同名规则查找配套摘要。若出现多个候选摘要，不应任意选择。

如果 PDF 不存在，停止发送并记录错误。不自动生成 PDF，不降级为摘要模式。

如果 PDF 存在但配套摘要缺失、无法读取或无法可靠匹配，同样停止本次发送并记录错误，不单独发送 PDF，也不重新生成摘要。

### 7.5 文件完整性与路径安全

发送前应验证输入文件类型和大小，确保 PDF 是现有报告附件，而不是凭路径误选的无关文件。日志中尽量记录报告 ID、文件名和处理结果；不应记录完整报告的全部内容或敏感的绝对路径，除非项目现有日志策略明确要求。

## 8. 发送模式

模式值统一使用 `summary`、`full` 和 `summary_pdf`。CLI、配置和定时模板应采用一致的模式命名。

### 8.1 摘要模式：`summary`

读取报告中已经生成的摘要，转换成适合微信阅读的文本消息后发送。不得调用 LLM 重新提炼，也不应从不相关的最新报告里拼接摘要。

若摘要为空、无法读取或与报告配对失败，停止发送并记录原因。

### 8.2 完整报告模式：`full`

读取已生成的完整报告文本。若正文超过 iLink Bot 接口允许的消息长度，按照所使用的接口版本所规定的限制进行分段。

分段规则应尽量在段落、标题或其他安全边界处分割，不应切断 UTF-8 字符。多段消息应标明顺序，必要时带上报告标题和段落编号，使收件人可以识别各段所属的报告。

分段长度上限应从已验证的接口实现中确定并集中定义，不要散落在多个模块中，也不要随意沿用其他聊天平台的限制。

### 8.3 摘要加 PDF 模式：`summary_pdf`

先发送已有摘要，再发送与该报告对应的 PDF 附件。两项内容必须来自同一次报告生成结果。

只有在摘要、PDF 和收件人状态均验证通过后，才开始执行发送流程。由于摘要消息与文件附件可能是两个独立接口请求，网络故障时不能假定二者具有原子性。日志必须能够区分摘要发送、附件发送以及整组发送是否完成。

如果摘要已成功发送但 PDF 发送最终失败，应记录部分成功状态。重试处理应尽可能只重试失败的那一部分；不得因简单重跑整组流程而无条件重复发送已确认成功的摘要。

## 9. CLI 设计

以下命令是目标接口设计，需要在实施时按现有 argparse、Typer 或其他 CLI 框架的实际使用方式对齐。

### 9.1 独立发送命令

```bash
# 登录并绑定个人微信
news wechat login

# 查看微信配置和绑定状态
news wechat status

# 默认发送最新报告，使用全局默认模式
news wechat send

# 明确指定发送摘要
news wechat send --mode summary

# 发送完整文本报告
news wechat send --mode full --file /path/to/report.md

# 发送摘要并附上已有 PDF
news wechat send --mode summary_pdf --file /path/to/report.pdf
```

不提供 `--mode` 时，使用全局默认模式 `summary_pdf`。不提供 `--file` 时，选择最新一份成功生成的报告。

如果指定的是 `summary_pdf` 模式，`--file` 应为 PDF 文件；摘要由报告解析器定位。参数与文件类型不匹配时应直接报错。

### 9.2 集成现有报告命令

现有 `news report` 命令增加显式的微信发送选项，例如：

```bash
news report --hours 24 --formats <现有报告格式参数> --send-wechat
```

也可以覆盖默认发送模式：

```bash
news report --hours 24 --formats <现有报告格式参数> --send-wechat --wechat-mode summary
```

上例中的 `<现有报告格式参数>` 是占位说明，不是可直接执行的字面参数。实现时应遵循项目现有的 `--hours` 和 `--formats` 参数语法。

只有显式提供 `--send-wechat` 才触发发送。没有该参数时，`news report` 的原有行为保持不变。

集成流程应当是：

1. 执行现有报告生成流程。
2. 检查报告命令是否成功。
3. 根据本次生成结果确定摘要、完整报告和 PDF 文件路径。
4. 调用微信发送服务，默认使用全局模式；显式指定 `--wechat-mode` 时使用临时覆盖值。
5. 返回能够区分报告生成失败、微信发送失败和全部成功的退出状态。

不应仅根据全局最新文件推测刚生成报告的位置，以免并发报告任务互相干扰。优先将本次报告生成结果中的明确路径传给发送服务。

### 9.3 CLI 行为约束

- 发送前检查登录状态与收件人绑定状态。
- 必要配置缺失时返回非零退出码并给出修复方式。
- 失败时打印简洁错误信息，并在日志中保存诊断详情。
- 不把令牌、上下文凭据或完整认证响应打印到终端。
- 对非交互式定时执行，不得无限等待二维码扫码或输入用户确认。
- 同一命令重复运行应有明确、可理解的结果；不应通过隐藏状态让用户误以为报告已成功发送。

## 10. 定时推送设计

### 10.1 调度职责

定时调度由操作系统负责，不在 NewsAgent 内增加常驻后台调度器。NewsAgent 只提供可被调度器调用的 CLI 和配套模板。

模板及说明应覆盖：

- macOS `launchd`。
- Linux `cron`。
- 需要时提供可扩展到其他系统的说明，但首期以以上两种为目标。

用户自行复制、修改和安装模板。安装或卸载期间不由 NewsAgent 自动修改系统任务表、LaunchAgents 或系统级配置。

### 10.2 固定每日时间

定时频率为每天一个固定时间，例如每天 08:00。默认时区是运行机器的本地时区。操作系统负责时区和夏令时行为。

配置模板应说明：

- 时间使用 24 小时制。
- `cron` 使用主机配置的本地时区，具体行为受目标系统的 cron 实现和系统设置影响。
- `launchd` 使用目标机器的日历时间机制，其睡眠、关机及错过触发时间后的行为应以目标 macOS 版本实测和相应文档为准。
- 若计算机在预定时间关机或不可用，不能承诺任务一定按原时间运行；应避免保证操作系统无法保证的执行时机。

### 10.3 两种定时运行方式

**方式一：生成报告后发送。** 系统调度器调用现有报告命令并显式启用微信发送。报告生成是现有流程，微信发送模块仍只负责消费生成结果。报告命令失败时，不发送本次消息、不回退发送旧报告，记录错误后等待下一次任务。

**方式二：发送已有报告。** 系统调度器直接调用 `news wechat send`，发送最新报告或指定文件。发送前应验证报告存在且完整；若本次发送所需的文件缺失，则记录错误，不擅自生成报告。

以上两种方式共用全局默认发送模式。定时任务可以显式覆盖为 `summary`、`full` 或 `summary_pdf`。

### 10.4 模板交付内容

建议在项目文档或示例目录中提供：

- 一份 macOS `launchd` 每日任务模板。
- 一份 Linux `cron` 示例。
- 可选的执行脚本示例，用于固定虚拟环境、工作目录、环境变量和日志路径。
- 模板安装、手动验证、查看日志、禁用和移除任务的操作说明。

模板应使用用户本机的绝对路径，不应假设定时进程自动继承交互式 shell 的 `PATH`、虚拟环境、当前目录或环境变量。不得将真实凭据写入 plist、crontab 或脚本内容。

### 10.5 定时任务防重复

应使用轻量的任务锁避免同一任务尚未结束时被再次并发启动。对于操作系统重复触发或人工重复执行，建议基于任务标识、计划日期和已完成状态进行审慎的重复执行保护。

去重机制不能阻止用户有意手动重发历史报告。手动发送与定时发送应分别记录来源及执行 ID。

定时推送成功后记录报告标识、执行时间、所用模式以及完成状态。仅在能够确认发送完成时标记为成功。

## 11. 失败处理与重试

### 11.1 默认重试参数

| 参数 | 默认值 |
| --- | --- |
| 最大重试次数 | 3 次 |
| 单次等待间隔 | 10 秒 |
| 是否将首次发送计入重试次数 | 否 |
| 是否可配置 | 是 |

因此，正常情况下最多进行一次首次发送和三次重试。配置文件中的重试参数必须经过类型和范围校验；非法或负值配置应报错，而不是静默转换成其他值。

### 11.2 错误分类

| 类别 | 默认处理 |
| --- | --- |
| 短暂网络错误、连接超时 | 按配置重试 |
| 服务端临时错误 | 在接口允许的情况下按配置重试 |
| 限流 | 优先遵循接口明确提供的重试提示；如与本地策略冲突，以协议要求为准 |
| 认证失效或令牌无效 | 记录错误并提示重新登录，不通过相同凭据无限重试 |
| 收件人未绑定或绑定信息失效 | 停止发送，提示重新绑定或检查上下文 |
| 输入文件缺失、摘要缺失、PDF 缺失 | 不进行网络重试；修复输入后重新运行 |
| 文件无权限、格式不支持、配置无效 | 停止发送并给出修复说明 |
| 消息过长或请求参数无效 | 修正内容或参数后再试，不重复提交相同无效请求 |

默认只对合理的可恢复发送错误进行网络重试，避免对确定性错误重复消耗请求。若协议明确要求对某一响应采取不同处理方式，应按协议实现并记录原因。

### 11.3 重试与重复消息风险

网络请求超时时，客户端可能无法判断服务端是否已经接收或发送消息。此时再次提交可能造成重复消息。如果接口支持可靠的消息 ID、幂等键或发送状态查询，应优先利用它们。若接口不支持，则必须承认该限制，不能声称所有发送都具备严格的恰好一次语义。

对于多段文本或摘要加 PDF 的组合发送，应分别跟踪每个消息段、摘要消息和附件的状态。在能够准确识别已成功部分的前提下，只重试未成功部分。

### 11.4 达到最大重试次数

重试用尽后：

- 记录最终失败结果、错误类别和重试次数。
- 以非零退出码结束命令。
- 保留报告文件，不自动删除或覆盖。
- 不自行启动常驻恢复进程。
- 等待用户重新执行或下一次系统定时任务。

日志不应包含完整令牌、授权二维码内容或不必要的个人消息正文。

## 12. 日志与状态记录

每次发送应尽量记录：

- 执行 ID 和发送来源（手动、报告命令集成或系统定时任务）。
- 报告标识或文件名。
- 发送模式。
- 开始时间、结束时间和耗时。
- 总尝试次数及每次失败的错误类别。
- 摘要、正文各分段和 PDF 附件的独立状态。
- 最终结果：成功、失败或部分成功。

不得在普通日志中写出完整登录凭据、上下文令牌或认证响应。若需要显示收件人信息，应做最小化处理；`status` 命令只显示确认绑定所需的非敏感摘要。

日志应遵循 NewsAgent 现有的日志习惯。对于定时任务，还应让用户能够通过模板中的标准输出、标准错误或配置的日志路径诊断问题。不要让一次网络故障导致无限增长的日志文件。

发送状态记录应允许程序识别某次任务已成功，但不应将其作为唯一的报告数据来源。状态记录损坏时，应明确提示并采取保守处理，避免误报成功。

## 13. 安全设计

1. 凭据和收件人状态仅保存在本地受保护目录，不提交到版本控制。
2. 使用 TLS 与服务端通信，并验证接口响应。
3. 不记录令牌、二维码内容或完整认证信息。
4. 对绑定操作进行明确确认，避免其他入站用户抢占固定收件人。
5. 读取报告文件时验证路径、可读性和文件类型，不把任意路径当作可信 PDF 或报告。
6. 对配置文件中的重试参数、时间、模式及路径做输入校验。
7. 不将凭据复制到 `launchd` plist、crontab、命令行参数或公开日志中。
8. 退出或解绑时清除相应本地账号和收件人状态；已生成的新闻报告不受影响。
9. 按移植代码的原始许可证和第三方依赖许可证执行合规检查。
10. 认证失效、协议响应变化和上下文过期应返回明确诊断，而不是无限轮询或静默丢弃消息。

## 14. 协议实现与兼容性要求

正式实现前，应从选定的 Hermes Python 实现中梳理完整的登录和发送协议路径，而不是只复制发送请求函数。至少检查：

- 二维码申请、轮询和登录成功确认。
- 认证凭据的格式、存储和续期机制。
- 入站消息长轮询及收件人标识提取。
- 上下文令牌等必要会话字段的获取、持久化与有效期。
- 文本消息、分段发送和文件附件的接口形式。
- 错误码、限流提示和临时故障处理。
- Bot 与个人用户之间主动发送消息的约束。

尤其应验证：首次绑定后，系统是否可以在之后的定时任务中，使用保存在本地的收件人信息和协议上下文发送主动消息。如果上下文有有效期或必须通过入站消息更新，必须按协议规定处理，并在失效时提示重新建立会话；不得把一次入站消息的令牌假设为永久有效。

如果 iLink 接口版本调整，客户端应把协议相关常量、请求构造和响应解析集中到适配层。对未识别的关键响应，不应按成功处理。

## 15. 测试方案

### 15.1 单元测试

- 配置解析、缺省值和无效配置校验。
- 文件权限设置及敏感文件读写。
- 报告解析器的最新报告选择。
- 同一报告的摘要与 PDF 配对。
- 三种模式的输入校验。
- 文本分段边界、非 ASCII 字符及 Markdown 内容。
- 错误分类与重试次数、等待间隔。
- 发送记录、重复任务锁和部分成功状态。

### 15.2 集成测试

应使用可替换的 iLink 客户端或模拟服务验证以下场景：

- 登录成功和登录失败。
- 首次绑定成功、重复绑定保护及解绑后状态。
- 收件人和上下文缺失、过期或失效。
- 摘要发送成功。
- 完整报告分段发送。
- 摘要加 PDF 的完整成功流程。
- PDF 缺失时停止整个发送流程。
- PDF 对应摘要缺失或匹配不唯一时停止发送。
- 网络失败后重试；达到最大次数后退出并记录错误。
- 摘要发送成功而 PDF 发送失败时记录部分成功。
- 报告生成失败时不发送，也不回退使用旧报告。
- 定时任务重复触发时避免并发重复执行。

### 15.3 端到端测试

在专用测试账号上确认：

- 可以完成真实二维码登录。
- 用户主动向 Bot 发消息后可以完成固定收件人绑定。
- 可以向该个人微信发送摘要、长文本和 PDF 附件。
- 应用退出后，凭据与绑定状态仍按预期保存。
- 后续独立 CLI 进程能够在没有 Hermes/OpenClaw Gateway 的情况下发送消息。
- `launchd` 和 `cron` 在目标机器的实际环境中可以调用对应 CLI。
- 认证或上下文失效时，错误信息和恢复操作清楚可理解。

不能仅使用模拟接口就宣称第三方协议已经验证；真实端到端测试结果需单独记录。

## 16. 验收标准

功能达到以下标准后，才视为满足设计目标：

1. 用户无需启动 Hermes 或 OpenClaw Gateway，即可通过 NewsAgent 发微信。
2. 首次登录通过二维码完成，随后可将一个个人微信绑定为固定收件人。
3. 绑定完成后，其他入站用户不能无确认地覆盖该收件人。
4. 默认 `news wechat send` 可发送最新报告，并使用全局默认的摘要加 PDF 模式。
5. 手动发送可通过命令参数覆盖发送模式或指定单个文件。
6. 三种模式均读取现有报告数据；发送模块不生成新的摘要或 PDF。
7. 摘要加 PDF 模式在附件或摘要缺失时明确失败，不静默降级。
8. `news report` 在显式提供微信选项后，能够在报告生成成功的前提下发送报告；不带选项时保持原有行为。
9. 每日定时任务可以使用操作系统模板配置，支持生成后发送和发送已有报告两种方式。
10. 报告生成失败时，本次不发送，不回退发送旧报告。
11. 默认网络重试最多 3 次，每次失败后等待 10 秒；配置可以覆盖这两个参数。
12. 日志能够区分成功、失败和部分成功，并且不会泄露认证凭据。
13. 文档提供安装模板和清晰的手动验证、查看日志、禁用任务的方法。
14. 代码许可、第三方依赖和真实 iLink 协议限制均经过检查。

## 18. 实施注意事项

- 所有命令名、配置字段和发送模式应在代码与文档中统一。
- 本设计中的新 CLI 参数为拟新增接口，不代表现有版本已经实现。
- 不应为了微信发送而重写现有报告生成流程；应复用其生成结果。
- 如果现有报告文件缺乏可靠的摘要与 PDF 对应关系，实现时应优先补充轻量的报告元数据或明确的配对规则，而不是根据修改时间猜测。
- 系统定时任务执行的 CLI 必须使用绝对可执行路径、正确工作目录和必要环境配置。
- 发送失败不能被打印成成功；部分成功不能被记录为完整成功。
- 对第三方接口未明确保证的功能，例如令牌永久有效、失败请求可严格去重或计算机睡眠后一定补执行，不得在使用说明中作保证。
